## 1. 目標與非目標

### 目標

讓**教學藥師**上傳院內藥品清單（純藥證字號），產生一條可分享的連結；
**新進藥師／實習生**點開後，站台只用院內實際有的品項出題，
用來訓練「認得院內架上的藥」。

### 非目標（本批明確不做）

| 不做 | 理由 |
|---|---|
| **個人進度追蹤** | 劃入 V5.1。要先定義「練過」＝答對幾次、提示答對算不算、換清單後舊進度怎麼辦、schema 怎麼遷移 |
| **院內版的最佳紀錄** | **v5.1 新增的非目標**（依判定 4.2）。院內版只顯示當回合分數。理由見 D40 |
| **院內相似藥配對報表** | 對病安有獨立價值，但與「新人訓練」目標正交 |
| **後端、帳號、進度回收** | D2 定案零後端。教學藥師看不到新人進度是已知且接受的代價 |
| **多分頁即時同步** | **v5.1 新增的非目標**（依判定 1.12b）。不做 `storage` event，接受 last-writer-wins |
| **超過上限時的檔案分享 fallback** | **v5.1 新增的非目標**（依判定 4.4）。超限直接拒絕，見 D42 |
| **針劑／外用／眼藥等非口服劑型** | **來源資料集完全不含這些**（見 D37.1 實測）。口服液劑與散劑雖在來源中，但無外觀圖可辨識 |
| **多租戶／清單保存於伺服器** | 連結即清單，無伺服器狀態 |
| **改變既有通用版行為** | 未載入院內清單時，站台行為必須與 v4.7 完全一致 |

## 2. 資料模型與名詞

| 名詞 | 定義 |
|---|---|
| **原始輸入** | 使用者貼上或上傳的整段文字 |
| **token** | 依 D35.1 切分規則從原始輸入切出的單元 |
| **canonical id** | token 經 D35.2 正規化後的藥證字號字串。**清單的唯一權威表示** |
| **院內清單**（formulary） | 一組 canonical id 的**集合**（無序、無重複） |
| **命中**（matched） | 該 canonical id 在 `pool.json` 的 `items[].id` 中存在 |
| **未命中**（unmatched） | 不在 `pool.json`，再分三類，見 D37 |
| **N** | **命中品項數**（matched items） |
| **K** | **該級別可出題的答案鍵數**。K ≠ N，**任何 UI 文字不得用 N 代替 K**（判定 1.14） |
| **院內版／通用版** | 是否載入院內清單的兩種站台狀態 |

**join key 已存在**：`pool.json` 的 `items[].id` 就是藥證字號，**3941 筆完全唯一**
（2026-08-10 `update-pool` 後；`source_version = 2026-08-10`、`source_rows = 6295`）。

## 3. 架構決策

### D34 連結編碼格式（wire format）

依判定 2.2／2.3／1.5／1.13／4.5 大幅修訂。

#### D34.1 編碼「來源已知 id」＋第三類計數

依判定 r2-4.1／2.5／1.1 修訂。**U4 至此結案。**

payload 攜帶：

1. **全部「來源已知」的 canonical id** —— 即命中 `pool.json` **或**存在於 `excluded.json` 者
2. **第三類的筆數**（不含 id 本身），供接收端揭露

**為什麼不編碼第三類 id**：三個理由疊加。
(a) 第三類多為針劑／外用／眼藥，**永遠不會進入這份口服外觀資料集**（D37.1 實測），
所謂「日後恢復」的收益在它們身上幾乎不存在；
(b) 它們卻會撐爆 D42 的上限——實測全院清單 1500 筆 → 2344 字元 → 直接被拒；
(c) **未知前綴的 id 本來就編不了**（D34.4），若堅持編碼全部 id，D34.1、D35.2、D37.1
三條規格互相矛盾（判定 r2-1.1）。

**為什麼不編碼 matched-only**：Q2–Q5 的品項（無圖／無刻字／答案鍵過短）**確實可能**
在日後的資料集補上外觀資訊而變成可出題，那個恢復收益是真的。

**代價（已明列）**：第三類品項日後若進入資料集，**不會自動恢復**，須重新產生連結。

**為什麼仍要帶計數**：使用者在需求階段選「全額揭露」的理由是防**虛假完成感**。
若接收端看不到「另有 N 筆院內品項不在外觀資料集中」，那個目標在接收端就落空了。

因此 codec **必須能編碼目前 pool 之外、但在 `excluded.json` 中的 id**。

#### D34.2 二進位格式（不可變 wire contract）

依判定 r2-2.2 補完。**只寫「varint」與「CRC-32」不足以產生跨實作一致的結果**，
以下每一項都必須精確到沒有第二種解讀。

```
payload   = base64url( body )
body      = header ‖ groups ‖ checksum

header    : byte 0      formatVersion   = 0x01
            byte 1      prefixTableVer  = 0x01
            bytes 2..3  count           uint16 big-endian（id 總數）
            bytes 4..5  unlistedCount   uint16 big-endian（第三類筆數，見 D34.2a）

groups    : 依 prefixIndex 嚴格遞增排列，每組為
            varint prefixIndex
            varint groupCount
            varint delta × groupCount

checksum  : 末 4 bytes，CRC-32/ISO-HDLC of（header ‖ groups），uint32 big-endian
```

**varint** ＝ **unsigned LEB128**：低位在前，每 byte 低 7 bits 為資料、
最高位為 continuation flag。**最多 5 bytes**；第 5 個 byte 的資料位超過 32 bits
即為 overflow → 拒絕。所有值皆為 unsigned，無 zigzag。

**CRC-32 variant ＝ CRC-32/ISO-HDLC**（即 zlib／PNG 使用者）：
polynomial `0x04C11DB7`（reflected `0xEDB88320`）、init `0xFFFFFFFF`、
input reflected、output reflected、final XOR `0xFFFFFFFF`。
檢查向量：`CRC32("123456789") === 0xCBF43926`（此向量須寫進測試）。

**base64url**：字母表 `A-Z a-z 0-9 - _`，**無 `=` padding**。
**最後一個字元所攜帶的未使用低位 bits 必須全為 0**，否則同一 body 會有多個合法字串表示，
破壞 canonical 唯一性 → 解碼時視為非法。

**號碼上限**：`2^32 − 1`。（實測來源最大 62392，遠低於上限；上限只為封閉 overflow 行為。）
另受 D34.4a 的 `numWidth` 約束：超過該 index 的位數上限即為非法。

##### D34.2a `count` 與 `unlistedCount` 的語意與邊界（v5.5 依判定 R3-3）

第三類（`UNLISTED`）沒有 canonical id，因此「算什麼」必須明講，否則
重複列、全半形、空白差異會讓兩個實作者算出不同的值 → **不同 header → 不同 CRC**。

| 欄位 | 語意 |
|---|---|
| `count` | payload 實際攜帶的 canonical id 個數（**去重後**） |
| `unlistedCount` | 經 D35.1 切 token、D35.2 正規化後，**去重的相異 token 數**中，
既不在 `pool.json` 也不在 `excluded.json` 者的個數 |

計數時點：**去重之後、編碼之前**。

**兩個 uint16 欄位超過 65535 一律拒絕產生連結**，
**不得截斷、不得 modulo**（那會靜默產生一個數字錯誤的合法 payload）。
註：D42 的 1800 字元上限使 `count` 遠達不到 65535，但 `unlistedCount` 理論上可能
（一份含大量針劑的清單），因此這條不是空談。

#### D34.3 canonical 規則（同一集合只有唯一合法編碼）

1. `prefixIndex` 在 groups 中**嚴格遞增**（不得重複、不得亂序）
2. 組內第一個 `delta` 是絕對號碼（**≥1**，實測來源最小號碼為 1），
   其餘 `delta` **≥1**（嚴格遞增，禁止重複 id）
3. varint 必須是**最短編碼**（禁止 `0x80 0x00` 這類冗餘 padding）
4. `count` 必須**恰等於**所有 `groupCount` 的總和
5. `groupCount` ≥ 1（不得出現空組）
6. **解碼終止條件**：讀滿 `count` 個 id 後，游標必須**恰好**停在 checksum 起點；
   多一個 byte 或少一個 byte 都是非法（不得有 trailing bytes、不得提前耗盡）
7. **`count === 0` 是合法 payload**（空清單），此時 groups 為空、
   `unlistedCount` 仍可非零。載入端視為「清單無任何可出題品項」，走 D38 三級全禁用路徑

**解碼時任一條件不成立 → 拋出明確錯誤，不得回傳部分結果。**

#### D34.4 前綴表 v1（不可變）

**必須從「來源資料集」導出，不是從 `pool.json` 導出**——見下方的實測教訓。

**「前綴」的定義**（v5.3 依判定 S-1 修訂）＝ **`…字第` ＋ 號碼段的非數字前置部分**。

#### D34.4a canonical id 的重建規則（normative）

**v5.5 依判定 R3-1／R3-10 新增。這是本規格最容易被漏掉、且漏掉會讓整個功能靜默失效的一節。**

D34 只定義了「id → bytes」，**沒定義「bytes → id」**。而整數化是**有損的**——
遺失的正是前導零。join key 是**字串完全相等**，因此若不補回，
decoder 產生 `衛署藥製字第123號` 而非 `衛署藥製字第000123號`，
**每一筆都會變成未命中，而 encoder 與 round-trip 測試完全正常。**

**實測依據**：來源 6295 列的號碼段字元長度分布為 `{"6": 6295}`——
**100% 固定 6 字元，零例外**。一般型為 6 位數字，`R` 型為 `R` ＋ 5 位數字。

**重建公式**（唯一合法形式）：

```
canonical_id = prefixString[i] ‖ zeroPad(number, numWidth[i]) ‖ "號"
```

**硬性規則**：

1. `prefixString` **包含「第」**，全部為上表的精確字串（不得自行拼接）
2. 號碼**必須零填補至 `numWidth`**；不足補零，**超過 `numWidth` 位數即為非法** → 拒絕
3. 結尾固定為 `號`
4. 全部為繁體中文全形字元，**不做任何大小寫或 Unicode 正規化**（`R` 恆為半形大寫）
5. **`prefixIndex` 超出該 `prefixTableVer` 的表範圍（本版為 0–17）→ 拒絕**，不得回退或猜測

#### D34.5 為什麼不用 bitmap-over-index

`update-pool.yml` 每月 1 日排程執行，`items` 沒有穩定全域排序。
月更後同一個 bit 指向**另一顆藥**，且**靜默錯位**——正是 repo CLAUDE.md 已寫死的最高風險
（「顯示 A 藥的照片、標成 B 藥的名字」）。藥證字號編碼與 pool 版本無關。

#### D34.6 為什麼不用文字編碼（判定 4.3）

文字格式體積必然大於 binary，而 D42 的上限已經很緊。維持 binary，
以 D34.2 的精確算法定義＋獨立 golden vectors 換取可稽核性。
Codex 第二輪明確表示不建議為簡化而取消 checksum 或改回 pool index（判定 r2-4.4）。

### D35 輸入解析與正規化

#### D35.1 tokenization 契約（判定 1.4）

**正式格式：純文字，每行一個 token。** 這是唯一保證支援的輸入形式。

| 情境 | 行為 |
|---|---|
| BOM | 剝除 |
| 換行 | `\r\n`／`\n`／`\r` 皆視為行分隔 |
| 空行、純空白行 | 略過，不計入任何分類 |
| 行首尾空白 | 剝除 |
| 一行含分隔符（`,`／`;`／Tab／全形逗號） | **視為多欄**，見下 |
| CSV／多欄 | 走 D35.1a 的明確指定契約；未指定時**拒絕整份輸入並要求指定**，不得猜測 |
| 引號包裹 | 剝除成對的 `"` 或 `'` |
| 整份輸入無任何 token | 提示並停止，不產連結 |

**不得猜測**是硬性要求：猜錯欄位會靜默產出一份錯誤清單。

##### D35.1a CSV／多欄的明確指定契約（v5.3 依判定 r2-1.3 新增）

v5.2 只寫了「不得猜欄位」，沒寫**使用者怎麼指定**。補齊本版最小契約：

| 項目 | 契約 |
|---|---|
| delimiter | **由使用者從固定清單選擇**（`,`／`;`／Tab／全形逗號），不自動偵測 |
| 欄位指定 | **1-based 欄序**（不依欄名——欄名編碼與空白變化太多） |
| header | 使用者勾選「第一列為標題列」時略過第一列，否則不略過 |
| 引號內的 delimiter | **不算分欄**（RFC 4180 行為）；引號未閉合 → 整份拒絕 |
| 各列欄數不一致 | **整份拒絕**並回報第一個不一致的列號，不做補齊或截斷 |
| 指定的欄序超出某列欄數 | 同上，整份拒絕 |

**一律拒絕而非略過**：略過會靜默產出一份不完整的清單，
而使用者無從得知少了哪些——與 D37.1 的誠實原則同源。

#### D35.2 canonical 正規化與整串比對

**實測依據**（來源 6295 列，2026-08-10）：忽略前綴只比號碼會撞號 **93 組、186 筆**，例如

#### D37.1 第三類的名稱不得暗示「使用者打錯了」

**v5.2 依實測整段改寫。實測依據**：來源 6295 列的形狀欄**只有**
圓形／膠囊／橢圓形／四邊形／三角形／六邊形／八邊形／水滴形／雙圓形／五邊形／
液劑（含糖漿用粉劑）／顆粒劑、粉劑或散劑／其他／空白。
**沒有針劑、沒有注射劑、沒有外用、沒有眼藥、沒有貼片。**

也就是說**這是一份「口服」藥品外觀資料集**。醫院清單裡的針劑、外用、眼藥
**完全不會出現在來源中**，因此會落入第三類——而不是 v5.1 以為的第一類。

因此第三類**絕對不能**叫「查無此藥證字號（請核對）」：教學藥師會看到數百筆
天天在用的針劑被標成「請核對」，直接不信任整個工具。

**且本工具無法區分「合法但非口服」與「字號真的打錯」**——兩者對這個資料集而言
都是不存在。**做不到的區分就不得假裝做得到。** 顯示文字必須誠實涵蓋全部可能：

> **不在外觀資料集中**（多為針劑、外用、眼藥等非口服劑型；也可能是已下市或字號誤植）

前綴不在 D34.4 表中者亦歸此類（且**不進 payload**，見 D34.1）。

**內部代碼與顯示名稱必須分開**（v5.3 依判定 r2-1.4）：程式內部一律用 `UNLISTED`，
**「查無此證」這個措辭在任何使用者可見之處都不得出現**。
v5.2 雖已定下這條，§5.2 的流程圖與 C50 卻仍寫著舊詞——已於 v5.3 一併清掉。

**stage precedence**：`stage` 是**首次淘汰階段**，順序固定 Q1→Q2→Q3→Q4→Q5。
一筆 id 只記錄一個 stage。

**前置條件（本批必須新增）**：目前 `pool.json` 只留下 3924 筆存活品項，
被篩掉的 2371 筆**沒有任何記錄**（`meta.stages` 只有計數）。
管線須額外產出 `data/excluded.json`。沒有它，第 1／2 類與第 3 類無法區分。

### D38 級別可用性＝實際組得出卷

依判定 2.1／4.6 **整段改寫**——這是本輪最重要的修正。

**`eligibleKeys().size` 不是可用性證據。** `eligibleKeys()` 是逐鍵局部判定
（`recordEligible` 不看整卷脈絡），而 `drawLeveledQuiz` 的 `excludeAns` 恆為
**整卷正解集合**（不變量 H2），因此 `.size ≥ 20` 與「能組出 20 題」之間**沒有蘊含關係**，
`QUIZ_ASSEMBLY_FAILED` 仍可能發生。這是 M5 的 M-11 同型錯誤。

#### D38.1 級別特定卷長（v5.3 依判定 r2-2.1 整段改寫）

**v5.2 的短卷模型對 L1／L2 在數學上不可能成立。** `buildChoices` 的 `excludeAns`
恆為整卷正解集合（H2），因此每題的誘答**只能從卷外的答案鍵取**：

```js
needDistractors = (level) => level === Level.L2 ? 5 : 3;   // L1 → 3、L2 → 5、L3 → 0
```

當卷長 ＝ K 時，`excludeAns` 吃掉全部 K 個鍵，**誘答一個都抽不到**。
v5.2 同時寫著「不得以重複題或跨子集誘答救場」——**我禁止了唯一能達成該卷長的兩條路**。

| 級別 | 每題需要的卷外誘答鍵 | 卷長上限 | 最小可用 K |
|---|---|---|---|
| L1 | 3 | **min(20, K − 3)** | 13 |
| L2 | 5 | **min(20, K − 5)** | 15 |
| L3 | 0 | **min(20, K)** | 10 |

（最小可用 K ＝ 最小卷長 10 ＋ 該級的誘答需求。）

#### D38.2 可用性判定的定義

1. **快速前置拒絕**：K < 該級的最小可用 K → 直接禁用（便宜，不必組卷）
2. **真正的證據**：以 D38.1 算出的目標卷長實際呼叫 `drawLeveledQuiz()`，
   **成功且 `validateQuizInvariants()` 回空**才算該級可用

組卷在允許的重試次數內仍失敗 → 該級**禁用**，顯示具體原因。
**不得以重複題或跨子集誘答救場**——那兩條路各自違反 H2 與 D36。

#### D38.3 判定必須可重現，且產物即第一卷（v5.3 依判定 r2-2.3／4.2 新增）

`drawLeveledQuiz` 是有限重試（`MAX_QUIZ_ATTEMPTS`）的**隨機**貪婪組卷，
同一子集在 seed A 成功、seed B 可能失敗。若把一次隨機結果當可用性，會出現
「檢查時可用、按下去失敗」與「重整後按鈕忽隱忽現」。

因此：

- probe 使用**下述 seed 協定**（v5.5 依判定 R3-2／R3-9 補完），與 `Math.random` 完全無關；
  相同 payload ＋ 相同 pool ＋ 相同 level **必須得到相同的可用性判定與相同的第一卷**

  **seed 協定（封閉契約，v5.5）**：

  | 項目 | 規定 |
  |---|---|
  | seed 輸入 | `payload`（base64url 字串原文）‖ `"|"` ‖ `level`（`"L1"`／`"L2"`／`"L3"`） |
  | seed 導出 | 對上述字串取 **CRC-32/ISO-HDLC**（與 D34.2 同一實作），得單一 **32-bit** seed |
  | PRNG | 沿用 `engine.js` 既有的 `makeRng(seed)`，**不另造** |
  | stream 數 | **單一 stream**。交給既有 `drawLeveledQuiz` 由其 `MAX_QUIZ_ATTEMPTS` 消耗 |
  | 外層重試 | **無**。不得在 `drawLeveledQuiz` 外再疊一層多 seed 重試（判定 R3-9） |
  | 子集排序 | 餵入 `buildIndex` 前，matched subset 依 **canonical id 的 code point 昇冪**排序 |

  **為什麼是單一 seed 而非序列**：v5.4 寫「固定 seed 序列」會讓人在既有三次內部重試之外
  再建一層，形成兩層策略與「哪一層決定第一個成功產物」的額外狀態。
  **Codex 已確認引擎內部沒有漏網的隨機來源**——只要傳入同一 `rng`，
  重試、抽正解、抽紀錄、洗牌全部走同一條 stream，因此單一 seed 即足夠。
- probe **成功時所產生的那一卷即為 ready state 的一部分**，
  使用者按下開始時**直接使用該卷，不得重抽**
- 這不是第二套可用性模型，而是重用真實產物（符合 D48）

**為什麼不用統一門檻**：實測 L2 在 60 品項以下就撐不住，L1／L3 到 20 品項都還可用。
統一硬擋會讓「換廠批次 30 品項」這個真實情境永遠用不了。

三級全部禁用時才拒絕產生連結。

### D39 短卷

短卷（卷長 < 20）的卷長由 **D38.1 的級別特定公式**決定，**不是 K**。
正解鍵集合是那 K 個鍵的**子集**（L1 留 ≥3、L2 留 ≥5 個鍵給誘答，L3 才可能等於 K）。
逐題檢討與當回合分數照常顯示。

**v5.2 曾寫「正解鍵集合恰等於那 K 個鍵」，該條對 L1／L2 不可能成立，已刪除。**

### D40 院內版不寫最佳紀錄

依判定 4.2／1.9／2.6 **整段改寫**。

**院內版完全不寫任何最佳紀錄**，只顯示當回合分數。
`tfda-drug-id-quiz:records-fx` 這個 key **從規格中刪除**。

**為什麼**：v5.0 原本要為院內版另開紀錄 key，但那立刻引出三個問題——
不同醫院的清單共用同一紀錄、換清單前後基準不同、月更縮水後基準又變。
而 D39 的論證（「基準不同不可比」）直接反噬自己。
個人進度本來就是明列非目標，V5.1 定義清單 identity 時再一起設計。

localStorage key（**前綴不可省**，本站與 pharmacy-portal 十幾個工具同源）：

| key | 內容 | 本批是否改動 |
|---|---|---|
| `tfda-drug-id-quiz:records` | 通用版紀錄 | **完全不動**（既有，schema 不變） |
| `tfda-drug-id-quiz:formulary` | 院內清單，schema 見 D45 | 新增 |

清除只能 `removeItem` 精確 key，**不可 `clear()`、不可前綴掃描**。
**讀取失敗時不得寫入**（既有紀律）。

### D40.1 退出院內版（v5.10，依 C51 人工留檔後的裁示新增）

v5.0–v5.9 只定義了「怎麼進來」，**從未定義怎麼出去**——`fx` 一旦載入就寫進 D45 的 key，
之後每次開站都會還原，使用者除了開 DevTools 刪 key 之外沒有出口。
這是規格缺口（C51 人工留檔時由使用者提出），不是刻意設計。

起始頁的院內版狀態列提供「切回全題庫」：

1. **二次確認走頁內元素**，不用 `window.confirm`（理由同「清除紀錄」：modal 阻斷整頁，
   且取消路徑無從自動驗證）。**取消時零 mutation。**
2. 確定時只 `removeItem` **`tfda-drug-id-quiz:formulary` 這一個精確 key**——
   不 `clear()`、不前綴掃描（沿用既有紀律），`records` 不得被波及。
3. **移除失敗時不得切回**：記憶體切了而 storage 還在，重整又會是院內版，
   而畫面已經說「已切回」——那比不給出口更糟。此時維持院內版並說明原因。
4. 成功後 `state.items`／`state.index`／`eligible`／`lookAlike` 全部換回全庫，
   **不能只改畫面**；級別的禁用狀態要跟著解除。

**代價（明列）**：清單從本瀏覽器移除後，要再用得重新開一次連結。
這是刻意的——保留一份「隱藏但還在」的清單，會讓下次載入的行為變得無法預測。

### D41 月更後品項消失＝降級，不阻斷

載入時以當前 `pool.json` 重新比對，得到 `missing`＝**payload 有、`pool.json` 沒有**的 id。

**v5.11 修正：`missing` ≠「已不在最新資料中」。**
v5.3 寫這一條時 payload 只帶命中的 id，兩者確實等價。**v5.4 的 D34.1 讓 payload
同時帶 `excluded.json` 的 id**（為了品項日後回到 pool 時能自動恢復）——從那一刻起，
`missing` 就恆含「一直都在資料集裡、只是不出題」的品項，而本條的措辭沒有人回來改。

實測：994 個藥證的真實院內清單，載入時顯示「**156 個品項已不在最新資料中**」，
而那 156 個一個都沒消失（55 非固體口服 ＋ 101 外觀題目品質不足）。
**對真實清單恆亮的警告，一個月後就沒有人讀了——那正是本條要防的事。**

因此 `missing` 必須先過 `splitMissing()` 分成兩類，**兩類的呈現強度不同**：

| 類別 | 判定 | 呈現 |
|---|---|---|
| `excluded` | id 在 `excluded.json` 內 | **muted**：「另有 N 筆在外觀資料集中，但外觀題目品質不足或非固體口服」。這是常態，教學藥師在產連結頁早就按類別看過同一批 |
| `absent` | 兩份資料都沒有 | **警告色**：「清單中 N 個品項已不在最新資料中，本次以 M 品項出題」 |
| 分辨不出來 | `excluded.json` 尚未到手或取不到 | **muted 且較弱**：「另有 N 筆院內品項目前不在出題範圍」。**不得示警，也不得靜默** |

- **分辨不出來時一個字都不能講成「消失」**：假警報比沒有警報更糟——
  它會把真的那一次一起淹掉
- 先畫弱措辭、`excluded.json` 到手再細分。**順序不得顛倒**（先講強的再改口＝先給一次假警報）
- `excluded.json` 只在 `missing` 非空時才抓。絕大多數清單完全不會多這次請求
- **持久化的 canonical payload 位元組不變**——**絕對不得覆寫成殘餘集合**（判定 1.14／C44）。
  覆寫會讓品項日後重新出現時也回不來
- 若縮水後某級掉到 D38 禁用條件，該級禁用；三級全禁用則提示重新產生連結
- **品項重新出現時自動恢復**（因為原始清單未被覆寫）

**已知限制（wire format v1 支撐不了的）**：連結沒有記錄「產生當下的可出題品項數」，
因此載入端分辨不出「一直都被排除」與「最近才從 pool 降級到 excluded」。
後者是真正的涵蓋範圍縮水，但要偵測它得改 wire format，代價遠大於效益。
本條只保證**不做不成立的宣稱**，不保證偵測得到所有縮水。

**實測觸發率**：2026-08-10 `update-pool` 前後，`pool.json` 的既有品項**一筆都沒有消失**
（3924 → 3941 為淨增加）。
D41 是**罕見路徑**（藥證下市或換證才會發生）。
因此 **C44 只能靠注入測試**，不可能等到真實資料自然觸發——
也正因罕見，實作若寫錯不會被日常使用發現。

### D42 硬上限與超限行為

依判定 2.7／4.4 修訂。

**上限量的是完整 URL 長度，不是 payload。** 硬上限 **1800 字元**（完整 URL）。

**2026-08-10 實測**：一份真實全院清單（1791 列）→ 進 payload 的「來源已知」id **481 筆**
→ payload 約 **856 字元** → 完整 URL 約 **907 字元**，**用不到上限的一半**。
`unlistedCount` ＝ 541（針劑等）。
**這同時證明 U4 那個張力在真實資料上不存在**——D34.1 改成只編來源已知 id 之後，
那 541 筆針劑根本不進 payload。當初改這條是為了解未知前綴的語意衝突，
順帶把長度問題也解掉了。

超限時：**明確拒絕產生連結**，並顯示「清單 X 品項，超出可分享連結上限，
請縮減清單或分批」。**不做「警告但仍產出」**——那會宣稱成功卻交付一條在部分平台會被
截斷的連結。**不做檔案 fallback**（列為非目標）。

### D43 URL 來源字串不得進入 DOM

解碼出的內容**只能**用於與 `pool.json` 的 `id` 做集合比對；
命中後渲染的一切（品名、圖片路徑）**一律取自 `pool.json`**。
未命中的 id 若要顯示或下載，須經 D35.2 正規化並**只經 `textContent` 類純文字 sink**，
不進 `innerHTML`、不進任何 attribute、不進 URL。

（V5 不攜帶 `?v=` 參數，見 D44.2。）

### D44 原子發布點與 URL 參數語意

依判定 1.7／1.6 新增。

#### D44.1 單一 commit point

**v5.3 依判定 r2-2.4 修訂。** v5.2 要求「記憶體、localStorage、URL 三者任一失敗時全部位元組不變」
——**這三個介面沒有共同 transaction，回滾本身也可能失敗**，那是平台提供不了的保證。
這是本 repo「規格文字強於任何合理實作能達成的範圍」的第四次。

改為平台真的做得到的三段語意：

1. **驗證階段**（解碼 → 取 pool → 比對 → D38 probe）：全部成功前**不發布任何一項**。
   任一步失敗 → 記憶體與兩個 localStorage key **位元組完全不變**，且 `fx` 保留在 URL
2. **提交階段**：先寫 localStorage（可能拋錯 → 視為失敗，回到第 1 點的保證）；
   寫入成功後，以**單一不會拋錯的記憶體狀態切換**發布
3. **清理階段**：URL 消費降級為**成功提交後的冪等 cleanup**，**不納入交易**。
   cleanup 失敗時保留 `fx`，但**不得回滾已成功載入的清單**——
   重整會以同一 payload 再跑一次，**active formulary 的語意相同**。

   **「冪等」限定在 URL cleanup 這個操作本身與 active formulary 的語意**（判定 R3-4）。
   **不宣稱 storage 位元組冪等**——D45 的 `savedAt` 是時間戳，
   同一 `fx` 重播必然產生不同位元組。驗收不得要求 byte-identical replay。

M5 的 D28.1 教訓（「資源前置條件成立後才發布」）對應到第 1 點；
第 3 點是本輪學到的新東西：**寫下「原子」兩個字時要先問「這個保證由誰提供」。**

#### D44.2 不使用 `?v=` 參數（v5.3 依判定 r2-2.6／4.3 刪除）

v5.2 曾規定 `v=<source_version>` 供「顯示與診斷」，同時又規定其值不得進 DOM——
**不能顯示就只剩診斷，而診斷輸出契約並不存在**。這條自相矛盾且無使用者收益。

**V5 的連結不攜帶 `v`。** 需要顯示題庫版本時，一律使用已驗證的 `pool.meta.source_version`。

#### D44.3 URL 消費的精確範圍

成功提交後**只移除 `fx` 一個參數**，其餘 query 參數與 fragment **精確保留**。
**載入失敗時保留 `fx`**（使用者可重整重試，且失敗不應讓連結消失）。

### D45 formulary 的 localStorage schema

依判定 1.8／4.5 新增。**URL 與 storage 共用同一份 canonical payload**，避免三套表示漂移。

```json
{
  "v": 1,                      // schema 版本
  "payload": "<base64url>",    // 與 URL 的 fx 完全相同的字串
  "savedAt": "2026-08-10T01:23:45.678Z",
  "srcVersion": "2026-08-03"   // 存檔當下的 pool source_version，僅供顯示
}
```

合法性條件：`v` 必須為已知版本；`payload` 必須能通過 D34.3 的完整解碼。
**任一條不成立 → 視為未載入院內清單（唯讀降級），且不得 mutation**——
不得「順手修復」或改寫（沿用 CLAUDE.md 既有紀律）。

matched subset 於載入後由 payload 導出，**不另存**。

### D46 一次只有一個進行中的操作

依判定 1.12 新增。產連結、載入 fx、切換級別皆為 active operation。
新操作使先前操作**失效**；**只有當前 operation 可以 commit**。
較舊的非同步結果晚於較新操作完成時**必須被丟棄**。

M5 已踩過「舊 Promise 搶回畫面」。

### D47 資料取得失敗的降級

依判定 1.11 新增。

| 情境 | 行為 |
|---|---|
| `pool.json` 非 200／JSON 損毀／schema 錯誤 | 既有 C4 失敗路徑（顯示「無法連線讀取題庫」） |
| `excluded.json` 取得失敗 | **通用版與院內版出題完全不受影響**；**產連結功能**停用並說明原因；院內版的 D41 訊息退回較弱但成立的措辭（v5.11） |
| 兩檔 `content_hash` 不成對 | 產連結功能停用；出題不受影響 |
| 產連結頁 | 兩檔**成對驗證通過**後才可產連結；任一檔失敗一律不產 |

**硬性要求：新增的 `excluded.json` 不得拖垮既有功能。**

**v5.11 補充：失敗要不要記住，由呼叫端決定，不由取檔函式決定。**
產連結頁**必須記住**（否則會拿半套分類去產連結）；起始頁為了 D41 的分辨而抓的那次
**不得記住**——開站時一次暫時性失敗會讓整個 session 都產不了連結，
而那次失敗與產連結這件事無關。

### D49 `excluded.json` 的資料契約（v5.3 依判定 r2-1.2 新增）

v5.2 只說「每筆 `{id, stage}`」，沒定義頂層 schema、版本與不變量。釘死如下：

```json
{
  "meta": {
    "schema": 1,
    "source_version": "2026-08-10",
    "content_hash": "sha256:…",
    "count": 2354
  },
  "items": [ { "id": "衛署藥製字第012345號", "stage": "Q1" } ]
}
```

**v5.9 修正**：v5.3–v5.8 的範例把 metadata 畫在**頂層**，
而 `data/pool.json` 的既有慣例是 `{ meta: {...}, items: [...] }`。
兩份資料檔放在同一個目錄、由同一個前端載入，卻用兩套 metadata 慣例，
是明確的維護陷阱——讀過 `pool.meta.count` 的人很自然會寫 `excluded.meta.count`。

那個範例是我在 v5.3 補寫 D49 時憑空畫的，**沒有對照手邊已經存在的 `pool.json`**。
這與本專案反覆出現的「從已處理的產物回推來源性質」是同一族：
**寫規格時沒去讀已經存在的權威樣本。**

**硬性規則：`data/` 底下的資料檔一律採 `{ meta, items }`，兩份的 metadata 慣例必須一致。**

**不變量**（任一不成立 → 整份 `excluded.json` 視為不可用）：

1. `schema` 為已知版本
2. `content_hash` 與 `pool.json` 的**完全相同**（D34 的配對識別）
3. `count` 恰等於 `items.length`
4. `items[].id` **兩兩相異**，且與 `pool.json` 的 id 集合**交集為空**
5. `items[].stage` ∈ `{Q1,Q2,Q3,Q4,Q5}`（封閉值域）
6. `items[].id` 非空字串

**單筆損毀＝整份不可用**，不做逐筆容錯——半套的分類資料會產生錯誤的排除原因，
比沒有分類更糟。降級行為見 D47：**產連結功能停用，出題完全不受影響**。

### D48 相容解法清單（防止錯誤補救）

依判定 2.8 新增。以下問題只准用對應解法，不得引入後端／jsdom／瀏覽器測試依賴／資料進 SW 快取：

| 問題 | 相容解法 |
|---|---|

| 管線雙檔原子性 | **兩檔各寫 `.tmp`，兩份都成功才 `rename`**（見下方說明） |
| 圖片與題庫快取 | 維持不進 SW（既有界線不動） |

## 5. 資料流

### 5.1 管線端（新增）

```
TFDA opendata 42 (6295 列，2026-08-10 快照)
  → build-pool.mjs
      ├→ data/pool.json      存活品項（既有）
      └→ data/excluded.json  被淘汰品項 {id, stage}（本批新增）
```

**id 聚合規則**（判定 1.2）：**2026-08-10 實測：來源 6295 列，id 全部唯一、無空白、零重複**，
因此此規則目前不會被觸發。仍寫進規格作為防禦，未來資料變動時行為才是確定的：
**任一列存活 → 該 id 算 matched**（進 pool，不進 excluded）；
**全部淘汰 → 取最早失敗階段**作為該 id 的 `stage`。
**結果不得依來源列順序改變。**

**規模實測**（2026-08-10，`update-pool` 後）：來源 6295 列、pool 存活 **3941**、
被淘汰 **2354**（Q1 572／Q2–Q5 1782）。`excluded.json` 原始體積約 **180 KB**，gzip 後約 36 KB。

`stage` 值域封閉為 `Q1`｜`Q2`｜`Q3`｜`Q4`｜`Q5`。

**配對識別以 `content_hash` 為準**（判定 2.4）——`build-pool.mjs:50` 的既有註解
自己寫著「同日重編有 `content_hash` 分辨得出來」，`source_version`（日期）只供顯示。
兩檔必須攜帶相同的 `content_hash`。

**成對寫出的原子性**（v5.9 依批次 2 覆審發現 4 改寫）：
兩檔各寫一份 `.tmp`，**兩份都寫成功才 `rename`**；任一步失敗則清掉暫存檔並中止，
既有正式產物**位元組不變**。

**為什麼不用 Actions staging**（v5.1–v5.8 曾這樣寫）：`carryHashes()` 是從 `--out` 指向的
路徑讀前版 `src_sha256` 的，若建置到隔離的 staging 目錄就讀不到前版，
所有 `src_sha256` 會變成 `null`，`fetch-images.py` 於是全量重抓 3,941 張圖——
**那正是 SC-3 那個回歸**（D10 宣告的增量判定形同未實作）。
`.tmp` ＋ `rename` 的作法同時保護 CI 與本機 CLI，且完全不動 workflow 的接力鏈。

**已知限制（誠實標明）**：`rename` 在多數平台是原子的，但**兩次 rename 之間**
若行程被殺，仍可能留下新 pool ＋ 舊 excluded。這個窗口是微秒級，
且 workflow 的 commit 步驟在 build 失敗時根本不會執行，
因此**發布層面仍是全有全無**。不為了關掉這個窗口引入交易性檔案系統。

## 6. 驗收條件

> 每條都須能回答「什麼樣的弱化實作會讓這條通過、但功能其實是壞的」。
> 〔堵〕標註要堵死的弱化版本。本節依判定書區塊 3 全面強化。

### A 組 — engine 純函式（`tests/formulary.test.mjs`）

**A36 整串比對，逐組驗完整撞號集合**
對**全部 93 組**跨前綴同號碼案例逐組斷言：canonical id 彼此不等、各自只命中自己那一筆。

**v5.4 修正**：v5.3 以前寫「27 組」，那是量 `pool.json` 的 3924 筆存活品項得到的。
**來源 6295 列實際有 93 組、186 筆。** 而 D34.1 讓 payload 也攜帶 `excluded.json` 的 id，
因此那 93 組**全部**都在工具的處理範圍內——照 27 組寫會有 66 組完全沒被驗到。
**這是「從過濾後的輸出導出來源性質」的第五次**（前四次見 §11）。
另對 D34.4 的**18 種前綴（含 16–17 的字母變體）逐一**釘住精確 canonical id，
並**至少一組獨立 wire golden vector 覆蓋新增的 index 11–17**——A36 只驗「解析」不驗 wire index 時，
codec 的 index 可以全錯而測試全綠（判定 r2-A36）。
**測試資料不得由受測 normalizer 自己導出。**
〔堵〕只 hardcode 5 組明列反例——其餘 22 組與其他前綴仍可錯配，而錯配直接造成 A 藥照片配 B 藥名。

**A37 正規化逐類驗，每類配反例，並驗冪等與不碰撞**
容忍類別各一條（全形數字、前後空白、內部空白、大小寫、前導零、缺 `第`／`號`），
**每類配一條不該被容忍的反例**（如 `第00123號` 與 `第01230號` 不得互相匹配；
純數字 `020174` 必須歸 `UNLISTED`）。另加：**組合輸入**（同時全形＋空白＋缺「第」）、
**冪等性** `N(N(x)) === N(x)`、**任兩個不同合法 id 正規化後不得相等**、未知前綴必須拒絕。
〔堵〕把正規化寫成「抽出數字就好」——所有單類容忍案例都會過。

**A38 golden vectors，不只 round-trip**
除 round-trip 外，必須有**獨立 golden vectors**：明列輸入集合、**精確的 encoded 字串**、
與 decoded canonical ids。案例須含 **pool 之外但格式合法的 id**，並釘住 `formatVersion`
與 `prefixTableVer`。
**golden 的 body bytes 與最終 payload 必須由人工推導或第二來源確認，
不得由受測 encoder 產生後抄回測試**——那只是 round-trip 的變形（判定 r2-A38）。

**已產出：`.ai-review/golden-vectors-v1.md`（G1–G5，2026-08-10，早於 codec 實作）。**
LEB128 位元組手算＋獨立實作交叉驗證（9/9 一致）；CRC-32 與 base64url 用 Python 標準庫
（`zlib.crc32`／`base64.urlsafe_b64encode`）當獨立 oracle。
**實作者須原封不動抄進測試；不一致時錯的是實作，不得回頭改 golden。**
矩陣須涵蓋：多個 prefix group、multi-byte varint、最小號碼 1、該 index 的最大合法號碼、
新增的 index 11–17、CRC byte order、以及 **`unlistedCount` 的兩種情形**（判定 R3-8）：
`count === 0 且 unlistedCount > 0` 的空清單，與兩者皆非零的一般情形。
每組 golden 都須附**由 D34.4a 重建出的 canonical id 字串**，證明補零規則被驗到。
〔堵〕`unlistedCount` 是 v5.3 才加的欄位，**codec 可以完全忽略它而現有 golden 仍全綠**。
〔堵〕(a) encode 與 decode **共用同一份錯誤的 prefix 表**仍可完美 round-trip——
**round-trip 測試本身證明不了正確性**；(b) 「獨立 golden」若沒有獨立 oracle，仍不是 golden。

**A39 canonical 唯一性**
對 ≥3 組（含跨前綴、含**最小合法號碼 1** 與該 index 的最大值）各做 ≥3 種順序的 permutation，
斷言輸出**位元組完全相同**，並與 A38 的 golden 一致。
〔堵〕只對測試那一組回固定字串。
**v5.5 修正**：v5.4 寫「邊界號碼 0」，但 D34.3 明定第一個絕對號碼 ≥1——
**合法編碼與驗收互相矛盾**（判定 R3-5，我自己的第七個矛盾）。
號碼 0 已移至 A40 的 grammar-invalid 類（重算正確 CRC 後斷言拒絕）。

**A40 解碼 fail-closed（依賴 D34.2 的 checksum）**
**必須分成兩類，否則只實作 CRC、完全不實作 canonical grammar 的 decoder 也會全綠**
（判定 r2-A40）：

**(a) 完整性測試**——對 body **每一個 byte 逐一翻轉至少 1 bit**，
**保留原本的 CRC 不重算**，斷言全部拋錯。**不得以「分段抽樣」代替逐 byte**
（v5.2 寫的那個逃生口已刪除），並須斷言 header／groups／checksum 三區段的 mutation 數皆非零。

**(b) canonical grammar 測試**——每個違規 fixture 都**重算正確的 CRC**，
確保拒絕來自 grammar validator 而非 checksum。逐一涵蓋：非最短 varint、
varint 超過 5 bytes／overflow、`count` 與實際不符、`prefixIndex` 不遞增或重複、
**`prefixIndex` 越界（> 17，但 CRC 正確）**、組內 delta 為 0、**號碼為 0**、
**號碼超過該 index 的 `numWidth` 位數上限**、空組、trailing bytes、提前耗盡、
base64url 尾端未使用 bits 非零、非 base64url 字元、
`formatVersion`／`prefixTableVer` 未知、**兩個 uint16 欄位的超界情形**。

另須有 `CRC32("123456789") === 0xCBF43926` 的標準檢查向量。
**每一種都必須拋錯且回傳值完全不存在**（不得回傳部分結果）。
〔堵〕v5.0 的寫法（四個 fixture）可被 hardcode 拒絕通過；且**若沒有 D34.2 的 checksum，
中段 bit flip 在數學上就無法保證被偵測**——那條驗收會逼出本 repo 最危險的假綠燈。

**A41 出題品項封閉於子集（防 vacuous pass）**
每卷**先斷言組卷成功且卷長正確**，再逐題驗**正解 item、全部 option item、spare item**
的 `id` 都在子集內，並驗 `validateQuizInvariants()` 為空。
另用**受控 RNG ＋ pool-only sentinel**（構造一顆只存在於全庫、不在子集的品項，
且讓它在誘答候選中排序靠前）強迫走可能洩漏的分支。
〔堵〕(a) 空卷讓逐題斷言 **vacuous pass**（迴圈根本沒跑）；
(b) 20 次隨機抽樣可能剛好沒抽到洩漏品項；(c) 只驗正解不驗誘答。

**A42 可用性判定：級別特定邊界＋真的組得出卷＋可重現**
以真實 `buildIndex` 構造精確 K，**三個級別的邊界各不相同**（D38.1）：

| 級別 | 須驗的 K 邊界 | 預期 |
|---|---|---|
| L1 | 12／13／22／23 | 12 禁用；13 短卷 10 題；22 短卷 19 題；23 正常 20 題 |
| L2 | 14／15／24／25 | 14 禁用；15 短卷 10 題；24 短卷 19 題；25 正常 20 題 |
| L3 | 9／10／19／20 | 9 禁用；10 短卷 10 題；19 短卷 19 題；20 正常 20 題 |

所有標記為可用的案例**都必須實際組卷成功並通過 invariants**。
另構造「K 過門檻但整卷組不出來」的敵意子集，斷言判**不可用**。
再以**規格化的固定 seed 集合**跑同一子集 ≥5 次，斷言判定結果**完全一致**（D38.3）。
〔堵〕(a) availability 只依 `.size` 回標籤，不證明能出卷；
(b) **三個級別共用同一組 K 邊界**——那正是 v5.2 的錯誤，會掩蓋 L1／L2 的誘答需求；
(c) 只用單一 seed，敵意子集恰好在該 seed 失敗就通過。

**A43 短卷的完整封閉性（級別特定）**
| 級別 | fixture 的 K | 預期卷長 | 正解集合 |
|---|---|---|---|
| L1 | 14 | 11 | K 的真子集 |
| L2 | **15** | 10 | K 的真子集 |
| L3 | 14 | 14 | 恰等於全部 14 鍵 |

三級都須驗全部 options 與 spares 封閉於子集、`validateQuizInvariants()` 為空。

**v5.5 修正**：v5.4 對 L2 用 K=14 並預期「卷長 ≤9」，
但 D38.1 已定 L2 最低 K=15、最低卷長 10 → **K=14 應直接禁用**。
A42 說禁用、A43 說有可驗題卷，實作無法同時滿足（判定 R3-6，我自己的第八個矛盾，
而且 A43 與 D38.1 是同一次編輯寫下的）。K=14 的 L2 案例只留在 A42 驗禁用。
〔堵〕沿用 v5.2 的「正解集合恰等於 K」——對 L1／L2 數學上不可能，
實作只能靠違反 H2 或跨子集誘答通過。

**A44 四分類逐 stage 精確 membership**
對 matched、Q1、Q2、**Q3**、Q4、Q5、來源不存在**逐筆**斷言精確歸屬類別，
再驗總和封閉與兩兩互斥。另加：重複 id、多重失敗的 precedence（斷言記錄**首次**淘汰階段）。
〔堵〕把所有 unmatched 錯分到同一類，**總和與互斥仍然成立**——
封閉性斷言證明不了分類正確。且 v5.0 完全沒測 Q3。

**A45 三種空／退化輸入，明列**
(1) 完全空字串；(2) 只有空白與分隔符；(3) 同一合法 id 重複 20 次。
逐一斷言**去重後的集合**與各分類的精確 membership，不只總和。
〔堵〕v5.0 寫「三種輸入」卻沒列出是哪三種——只要不拋例外且回四個空集合就會通過。

### B 組 — 管線（`tests/pipeline.test.mjs` 擴充）

**B10 逐筆驗精確輸出與 stage**
fixture 必須包含**每一個 Q stage 各 ≥1 筆**與**已知 survivor ≥1 筆**。
**Q2 的 fixture 必須是合成的**——實測來源中該 stage **只有 1 筆真實案例**
（`meta.stages`：Q1 572／Q4 1603／Q5 170／Q3 8／**Q2 1**），
實作者去資料裡撈第二筆會撈不到然後跳過（主持人自查 S-2）。
逐筆斷言落在 pool 或 excluded 的哪一邊與其 `stage`。另驗：來源列數、
**同 id 多列的聚合規則**（一列存活一列淘汰 → 必須進 pool）、輸入順序不影響結果、
既有的 pool 數量 gate、id 不可為空。
〔堵〕把所有 id 都塞進 excluded、pool 留空，**互斥與聯集仍然成立**——管線全綠但題庫消失。

**B11 stage 值域封閉**
對未知值、缺欄位、`null`、非字串、大小寫變體、含額外空白**逐一**驗管線 fail；
另加 Q1–Q5 全部合法的正面 fixture。
〔堵〕只拒絕指定的那個未知字串。

**B12 兩檔以 `content_hash` 成對，且失敗時位元組不變**
fixture **除 `content_hash` 不一致外完全合法**，斷言 fail **且錯誤原因正確**。
測試前先放置 sentinel 正式檔，失敗後斷言**兩檔位元組完全不變**。
成功案例另驗兩檔 `content_hash` 相同。
〔堵〕(a) fixture 因其他 schema 錯誤而 fail，測試看起來仍綠；
(b)「不得寫出任何檔案」偵測不到**先寫後回滾**，只證明了 exit code 非零。

**B13 前綴表完整性（v5.2 新增）**
管線必須掃描**來源全部列**（不是存活品項）的許可證字號前綴，
遇到**不在 D34.4 表中的前綴**時，以明確訊息**中止並列出該前綴與筆數**。
測試須注入 **≥2 筆**前綴為 `衛福部新式字` 的 fixture，且**刻意讓它們在 Q1–Q5 被淘汰**
（否則若它們存活，只掃 `pool.json` 的錯誤實作仍會通過——**完全沒堵住 v5.1 的真正失敗模式**，
判定 r2-B13）。斷言管線 fail、錯誤訊息含該前綴、**且含精確筆數**（不得硬寫「1 筆」）。
規格另明定：**前綴抽取必須發生在 allowlist 驗證之前**，
避免未知前綴先被 normalizer 丟掉而永遠掃不到。
另加正面 fixture：18 種前綴全數存在時管線正常完成。
〔堵〕(a) 只掃 `pool.json` 的存活品項——**這正是 v5.1 漏掉 5 種前綴的原因**，
存活品項的前綴分布是來源的子集；
(b) 只警告不中止——新前綴會靜默讓那些藥編不進連結，而使用者端只看得到「不在資料集中」。

**為什麼中止而不是放行**：新前綴出現代表 wire contract 需要升版，這是**人必須介入的決策**
（升 `prefixTableVer`、在表尾追加 index、確認舊連結相容）。
月更因此中斷是可接受的代價——沿用「發布是全有全無」的既有紀律。

### C 組 — 跨層（`tests/formulary-ui.test.mjs`）

**C40 揭露的數字與下載內容同源**
逐類斷言**精確的 id 集合**（非只比數量）；把下載內容**重新解析**後，
斷言 canonical ids、類別歸屬與順序契約與畫面資料**完全一致**。
〔堵〕UI hardcode 四個數字；下載檔只要筆數相同、內容全錯也會通過。

**C41 載入後出題封閉於命中集合（防 vacuous pass）**
每卷先驗組卷成功、卷長正確、invariants 為空，再逐題驗正解與**全部誘答／spares**。
用 pool-only sentinel ＋ 受控 RNG 強迫走洩漏分支。
〔堵〕空卷的聯集是空集合，自然是子集——這條是 D36 的核心跨層防線，假綠燈代價最高。

**C42 解碼失敗不得改變任何狀態**
先載入清單 A，再開一條損毀連結。斷言：完整記憶體 snapshot 相等、
**兩個 localStorage key 位元組全部不變**、**mutation call log 為空**、
`fx` 仍保留在 URL、且**錯誤後仍能從 A 正常組出一卷**。
〔堵〕只驗 formulary key 仍是 A——實作可改 `records`、`removeItem` 其他 key、
或清空記憶體後把畫面假裝成 A。

**C43 涵蓋數字的語意與可及性**
自動測試驗：答題頁與結算頁**都**存在語意節點、顯示的 **N 與 K 精確正確**、
且文字含範圍說明（措辭須與 D37.1 一致，不得寫成暗示資料集涵蓋針劑的說法）。**N 與 K 必須分別斷言，不得用 N 冒充 K。**
可見性與換行**移交 C51**。另加靜態契約確認節點未被無條件 `hidden`／不可及屬性遮蔽，
**該掃描器必須 fail-closed**（解析不出的規則直接失敗、掃到 0 條規則直接失敗）。
**另須驗狀態轉換後的數字**（判定 r2-C43）：同一 session 內切換級別時 **N 不變而 K 改變**、
月更降級後 **N 與 K 都改變**，各自斷言精確值。
靜態 scanner 須有**反向 sentinel**，分別證明它抓得到 (i) 節點自身 `hidden`、
(ii) **ancestor 的 hidden**、(iii) 規格列舉的各項不可及屬性。
〔堵〕(a) 樁上「DOM 有文字」不等於可見；(b) 對單一 fixture hardcode 正確 N/K，
**切級別或降級後仍顯示舊 K**——虛假完成感通常發生在狀態轉換後，不是初始 fixture；
(c) scanner 只查節點自身而漏掉 ancestor；(d) 判準漏了——M5 的 M-16 同型。

**C44 降級不覆寫原始清單**
指定消失的 id 與精確 survivors，斷言：**持久化的 canonical payload 位元組不變**、
active matched 集合精確縮小、可用性精確轉換、且**實際完成一卷**。
另驗**品項重新出現時自動恢復**。
〔堵〕「未清除」只看 key 存在——實作可能已把原清單覆寫成殘餘集合，
那會讓品項日後恢復也回不來。

**C45 禁用級別是「可見且程式化 no-op」**
分開斷言 (a) semantic disabled 狀態與原因文字存在、
(b) 程式化呼叫該入口前後，**完整 state／storage／timer／image-load call log 皆不變**。
〔堵：不得把 hidden 當 not-present〕（M5 的 M-6 判準）；
且入口可能偷偷改 level、啟動 preload、寫 storage 後才返回，最終畫面看似 no-op。

**C46 院內版完全不寫最佳紀錄**
先在 `tfda-drug-id-quiz:records` 放置高低不同的 sentinel，
院內版跑完**全對的 20 題正常卷**（不是短卷）後立即斷言該 key **位元組完全不變**
且 mutation call log 為空。短卷再驗一次。
〔堵〕v5.0 的寫法（短卷跑全對再看有沒有污染）混合了兩件事；
且「完全不記錄任何成績」也會通過。

**C47 通用版紀錄路徑仍然正常**
通用版跑一回合，斷言 `records` 的**精確預期更新**發生，
且 mutation call log **只含**該精確 key。
〔堵〕只驗「另一個 key 未變」——兩種模式都不寫也會通過，成績功能靜默失效仍全綠。

**C48 讀取失敗時所有 mutation 為零**
分別測：`localStorage` 不存在、property access 拋錯、`getItem` 拋錯、JSON 損毀、schema 不合。
每種都斷言 **`setItem`／`removeItem`／`clear` 呼叫次數皆為 0**，並覆蓋兩個本站 key。
〔堵〕v5.0 只禁 `setItem`——而「不可 `clear()`」正是 CLAUDE.md 白紙黑字的既有紀律。

**C49 URL 消費範圍精確**
原 URL 構造為含 `fx`、**無關參數**與 **fragment**（V5 已無 `v`，見 D44.2）。
成功後斷言**只移除 `fx`**，其餘**精確保留**；重跑完整啟動流程，
斷言**沒有第二次 formulary mutation**。失敗案例斷言 `fx` **仍保留**。
另驗 D44 第 3 段：**cleanup 失敗時已載入的清單不得回滾**。
〔堵〕刪掉整個 query string 就能通過「不含 fx」。

**C50 惡意字串走真實 decoder 路徑**
分兩層驗：
(a) **真實 decoder** 對含非格式字元的 `fx` **fail-closed**（不繞過 decoder 注入）；
(b) 分類與下載層：構造一個**經 D35.1 切出、含 HTML 語法字元的 token**，
**先斷言它確實經真實 tokenizer 抵達 `UNLISTED` 類、且出現在畫面資料與下載資料中**，
再驗它只經純文字 sink——**否則「零 sink 呼叫」可能只是惡意資料從未到達受測路徑**
（判定 r2-C50）。規格須列出零依賴樁**實際監控的完整 sink inventory**
（`innerHTML`／`outerHTML` setter、`setAttribute`、各 attribute property assignment、
`insertAdjacentHTML`、URL sink），並為**每一種**準備 sentinel 證明監控真的會觸發。
〔堵〕v5.0 的構造方式在 prefix＋number codec 下**根本不可能發生**，
等於繞過真實路徑；且只查最終 `innerHTML` 抓不到經轉形或進入 attribute 的 payload。
**監控須以現有零依賴樁實作，不得引入 jsdom。**

**C52 probe 的成功產物就是使用者按下開始後的第一卷（v5.5 依判定 R3-7 新增）**
D38.3 寫了這條要求，但 A42 只驗 availability 可重現、C41 只驗出題封閉性——
**實作仍可在按下開始時用 `Math.random` 重抽一次，而上述測試全綠**。

記錄 probe 產出題卷的**完整穩定 identity**（逐題的正解 id、全部 option id 與 spare id 的序列），
按下開始後**逐題斷言使用同一產物**；並斷言開始動作**沒有第二次組卷、沒有額外 RNG 消耗**
（以 RNG spy 計數，沿用 M5 的 M-2／M-20 手法）。
〔堵〕這正是第二輪指出的「檢查時成功、開始時失敗」的復發路徑——
而所有既有的封閉性測試都攔不到它，因為重抽出來的卷同樣封閉於子集。

**C51（人工留檔）最少留檔矩陣**
375px 下，**四種畫面各一張**：產連結結果頁（含四類數字表格）、答題頁、結算頁、
含禁用級別的起始頁。每張須為**完整畫面**（不得裁切），並標明：
瀏覽器與 zoom、viewport、**fixture identity**、實際 N 與 K、**觸控目標的人工量測數值**、
以及該張的獨立 verdict。
判定項目：不溢出、對比可讀、**觸控目標 ≥44px（須為量測值，不得目測「看起來夠大」）**。
〔堵〕沒有指定留檔組合時，只看一張首頁截圖也可宣稱通過——
**C39 就是因為這樣，今天早上只完成了一半**。

### 8.1 本次量測所用對應表的來源與限制（重要）

上述數字是用 `TFDA-drug-info-search/drugs_data.json` 的 `nhiMatches` 做健保碼→藥證對應
而得。**那份對應不可搬進本專案當權威**：該 repo 的 CLAUDE.md 明寫

> 成分比對採**寬鬆匹配**（空成分視為匹配成立）。收緊會使大量品項失去健保歸屬——
> **藥師查不到，比偶發誤配更危險**。現況 verified 98% / code-only 2%

**那是為相反的風險權衡調的**：查詢站怕「查不到」，而辨識測驗怕「誤配」——
誤配會讓新人把 A 藥的照片記成 B 藥的名字，是本專案最怕的失效模式。
因此該對應**只可用於量測量級，不可用於產品路徑**；
日後若真要支援健保碼輸入，必須自建一套收緊的對應並自行驗證，
且 `code-only` 那類一律不得靜默採用。
