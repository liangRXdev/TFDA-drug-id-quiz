結論：**目前不建議直接動工**。規格方向合理，但有 3 個會在完成後造成大幅重寫的核心缺口：

1. L2「照片實際可辨識」尚未被證明；`L2key` 只能證明文字資料不同。
2. `Question`／`Item`／答案鍵與顯示圖片之間的身分模型未定義，直接碰到最高風險「圖片與答案錯配」。
3. L2 提示後仍固定宣稱「亂猜基線 25」在數學上不成立，且與「淨高於基線」文案衝突。

以下僅依提供的規格文字覆審，未讀取 repo、未執行程式、未修改檔案。

# 區塊 1：需求與邊界缺漏

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | **答案鍵、紀錄與圖片的 canonical identity 未定義。** 題目抽樣單位是 `ans`，但 `buildChoices(correct, ...)` 接受的是 `Item`；同一 `ans` 可有多筆紀錄、不同 `full`、`zh`、外觀或圖片。A8/A9 又宣稱掃描「3124 個答案鍵」，沒有定義每個答案鍵選哪一筆紀錄、所有紀錄是否都必須可用。 | 實作團隊很可能各自選擇「第一筆紀錄」「隨機紀錄」或「任一可組題紀錄」。之後若發現題幹來自紀錄 A、圖片來自紀錄 B，將正中最高風險「答案與圖片錯配」，且抽題、選項、檢討、資源替換及測試都要一起重寫。 | 規格先定義單一題目的身分不變量：正解答案鍵如何選、同鍵紀錄如何選、L2 的 `full + zh` 與正解圖片必須來自同一紀錄、每個選項及備援都須保留其原始紀錄身分。並明定「答案鍵可用」是至少一筆紀錄可用，還是所有可能被抽到的紀錄都可用。 |
| **High** | **`Question[]` 的 v3 資料契約缺失。** 新增的 `options`、`answerIdx`、`spares`、使用者選擇、已排除格、目前圖片身分及 `level` 要放在哪裡完全未定義；同時又要求 `newQuestion()` 原樣沿用。 | 若先把部分狀態放 DOM、部分放 Question、部分放全域變數，之後處理遲到事件、檢討頁及成績計算時會發現無法重建真實作答歷程，必須重做狀態管理。 | 補一份規格層級的 v3 Question／QuizSession 欄位與 ownership 表，明定哪些是不可變題目資料、哪些是作答狀態、哪些只是畫面衍生值。這不要求改寫既有 `transition()`，但必須說清楚它與選擇題附加狀態的邊界。 |
| **High** | **H2 需要整卷全域資訊，但生成流程仍描述成逐題組裝。** `buildChoices` 必須排除本卷所有其他正解；當某題 `NO_DISTRACTORS` 後改抽下一個答案鍵，整卷正解集合也隨之改變，已完成題目的誘答可能立刻違反 H2。 | 若以單程逐題生成，H2 會偶發失效；若後期才修，通常要把整個抽題流程改成兩階段或整卷回溯。 | 明定整卷生成交易：先確定全部正解答案鍵，再以完整正解集合建選項；任何正解替換後，哪些題目必須重新驗證或整卷重建。`excludeAns` 應明定是否包含自己的正解及其精確語意。 |
| **High** | **L2 何時允許作答沒有定義。** 四張圖尚未全部成功解碼時若可點選，使用者可能在只看到部分選項時作答；若作答後才發生 `onerror`，已鎖定分數又可能被作廢或換圖。 | 這類 race 通常只在慢速手機或偶發網路下出現，會在 UI、狀態機與計分已完成後才暴露。 | 明定題目須在四個目前有效格都完成載入及解碼後才進入可作答狀態；載入期間選項、提示及放大行為如何處理；LOCKED 後的圖片錯誤是忽略、標示，還是回滾題目。 |
| **High** | **備援替換的原子性與併發規則未定義。** 可能同時有兩格失敗、替換圖再次失敗、已排除格失敗，或同一格連續送達舊 `onerror`。兩個備援是否彼此通過 H1/H3/L2key 也未明說。 | 若各格獨立處理，很容易重複消耗同一備援、留下重複 `ans`、讓 `answerIdx` 與畫面錯位，或使提示刪除到已被換走的項目。這些錯誤會污染所有後續作答及檢討資料。 | 規格定義一次替換的前後不變量：格位不變、選項身分原子更新、備援只能消耗一次、所有目前仍顯示的選項重新滿足 H1–H3/L2key、已排除狀態是否跟著格位或選項身分。並定義多個錯誤的序列化規則。 |
| **Medium** | **資源失敗只涵蓋 `onerror`，未涵蓋永久 pending、成功回應但無法 decode、零尺寸或錯誤 MIME。** | 外部主機不一定乾淨地回傳 404；連線掛住會讓整題永遠無法開始，也不會進入既有 fail 路徑。 | **[新增需求]** 若要保證回合可終止，需把「資源失敗」明確擴充為 HTTP/網路錯誤、解碼失敗及有限載入逾時，並定義逾時值與後續處理。不納入的具體後果是單一圖片可永久卡住整回合。 |
| **Medium** | **`最多重試 N 次` 的 N 未定義，也未定義耗盡時的使用者可見失敗。** `INSUFFICIENT_KEYS` 又被稱為「沿用既有語意」，但 L2 還有「可用答案鍵 <100 時前端明確報錯」這個不同門檻。 | 不同實作者會選不同 N，造成同一題庫與 seed 偶發成功或失敗；到 UI 整合後才會發現沒有可呈現的錯誤狀態。 | 明定 N 或改成與可用答案鍵集合大小有關的有限流程；區分「實際不足 20 題」「演算法嘗試耗盡」「品質紅線低於 100/3000」三種錯誤及其驗收方式。 |
| **Medium** | **兩個備援的適用級別未定義。** `buildChoices` 對所有 level 都回傳 `spares`，但 D15 只要求 L2，L1 只有一張圖片且沒有替換需求。 | 可能造成 L1 無意預抽甚至預載多餘資料，或測試誤以為 L1 也必須保證五個誘答。之後修改 API 會影響所有呼叫端。 | 明定 L1/L3 的 `spares` 是空集合、欄位不存在，或僅 L2 使用；同時明定「預抽」不等於「預載圖片」。 |
| **High** | **L2 提示後的亂猜基線與 D14 衝突。** 未提示四選一的期望分數是 25；提示後三選一且滿分 0.5，純猜期望分數是約 16.7。整卷基線取決於使用提示的題數，不會固定為 25。 | 若 `scoreQuiz()`、結果頁與 PNG 都先固定寫入 25，之後要改為實際基線將牽涉資料模型、文案、測試與既有成績卡；若不改，會違反「分數不可誤導」的既有風險控制。 | 二擇一先寫死規格：① `25` 明確改名為「未使用提示的四選一基線」，不得稱為本次作答的實際亂猜基線；或 ② 依每題是否提示計算本回合期望基線。若仍顯示「淨高於基線」，應採第二種。 |
| **Medium** | **L2 被提示刪去的格是否仍可點選未定義。** 「保持可見並標示排除」不等於禁止作答。 | 若仍可點，`judgeChoice` 會照常判定，使用者可能選一個系統明知錯誤的格；若 UI 自行禁止但狀態未記錄，檢討與自動測試無法驗證。 | 明定排除格的互動語意、鍵盤/觸控行為，以及其在題目狀態中的表示；同時定義替換與排除先後發生時的結果。 |
| **Medium** | **「預設不預選」只描述第一次進站，沒有定義重新開始、返回首頁或完成一回合後是否清除級別。** | 若沿用上一回合級別，正是 §5.1 想避免的錯誤；後期才補會牽涉導航及 session reset。 | 明定每次進入 `#start` 是否重設級別；若目標是每回合都明確選擇，C7 必須覆蓋第二回合，而不只首次載入。 |
| **Low** | **L3 提示內容在基準敘述中不一致。** 現況段落寫「首字母」，D16 寫「首字母 + 字數（現行）」。 | 實作者無法判斷「L3 不變」到底以哪一版為準，可能無意改變已上線功能。 | 在 v3 明確引用 v2 的確切提示輸出；若本次不得改，A17 類回歸條件也應涵蓋 L3 提示行為。 |
| **Low** | **「前綴包含」及比較前處理不夠精確。** 文件同時使用「其一為另一的前綴」「前綴包含配對」「去空白後」，但未說明大小寫、標點、Unicode 空白及相等字串。 | D13 將同時影響 eligibility、生成及測試；比較規則稍有不同就會重現 no_fuzzy 類漂移問題。 | 以規格文字固定比較輸入，最好明定直接使用既有答案鍵、只移除哪些空白、是否保留標點；相等由 H1 處理而不再算前綴碰撞。不得藉此修改 `normalize()`。 |

# 區塊 2：架構風險

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | **L2 的核心可解性只由 metadata 推論，沒有驗證實際照片。** `L2key` 不同只能證明資料列的刻字不同，無法證明四張 640px 圖中刻字可見、朝上、未反光、未被包裝遮住。規格自己承認「可解性完全押在刻字差異上」，卻把照片層留成上線後回報才處理的殘餘風險。 | 若實際大量不可辨，D12 的整個誘答方向、3000 鍵門檻、四宮格尺寸及「中級」定位都要重做；這不是調 CSS 能補救。 | 在全面實作前設一個人工可證偽的照片可辨識 gate：對稀有/常見形色、不同刻字長度、不同照片品質做分層抽樣，要求獨立檢視者僅靠規定畫面可分出正解。若未達門檻，先修改 L2 誘答原則，再進入實作。這是驗證既有可解性要求，不是新增使用者功能。 |
| **High** | **D17 同時宣稱 `scoreQuiz()` 原樣沿用，又要求新增 `chance` 並依 level 回傳不同值。** 現有簽名未包含 level，規格也沒說 level 從何而來。 | 實作時勢必有人讓 `scoreQuiz` 讀全域狀態、把 level 塞進每題，或私自修改簽名；之後測試與 Canvas 都會耦合到不同來源。 | 修正文義：區分「既有得分語意不變」與「函式介面不變」。若 25 只是顯示用的級別 metadata，應避免耦合到計分核心；若要算實際基線，則明定 level/hint history 的唯一資料來源與新介面契約。 |
| **High** | **號稱純函式，但 RNG 與 `Map` 候選陣列可能帶可觀察副作用。** partial Fisher–Yates 若直接改動 index 內陣列，同一 index 的後續題目會依呼叫歷史改變。 | 這會破壞固定 seed 重現、全題庫掃描及多回合一致性；直到出現順序相依的 flaky test 才會被發現。 | 規格明定 `items` 與 `PoolIndex` 在 `buildChoices`／`drawLeveledQuiz` 後必須保持內容與順序不變；若允許內部快取，也須與 RNG 結果無關且不可改變候選集合。 |
| **High** | **「抽到不可用才跳過」可能破壞答案鍵均勻抽樣，也可能在可用鍵很多時因隨機碰撞錯誤拋出。** | 平台既有原則明定抽樣單位是答案鍵。後期若發現 L2 某些鍵因候選多而更常出現，需重寫整卷生成器並重做統計驗證。 | 明定三級都是在各自「可用答案鍵集合」內等機率抽樣；不可把重試次數或候選紀錄數變成抽樣權重。驗收應測性質，而非只測成功湊到 20 題。 |
| **High** | **選項位置與畫面格位缺乏穩定身分。** `answerIdx`、提示排除 index、圖片 `src`、備援替換及 DOM index 都依同一整數索引，但替換或重新渲染可能使索引指向不同 Item。 | 一旦錯位，系統會把正確圖片判成錯誤答案，正中最高風險；而畫面外觀仍會完全正常，極難人工發現。 | 規格要求每格具有不可混淆的題目 token、格位 token 與目前 Item identity；判定、提示、替換、檢討都以同一題目快照為準。索引只能是該快照內的位置，不得成為跨渲染身分。 |
| **Medium** | **L2 將每題圖片請求由 1 張提高到 4 張，且有替換與放大，但沒有整回合圖檔流量驗收。** C14 明確排除題目圖片，因此無法證明仍符合「圖檔預算 ≤200MB」。 | 若圖片平均大小或重試率超出預期，手機端流量與載入時間會在功能完成後才暴露；屆時只能改圖片策略或題型。 | 增加既有平台限制的量測規格：正常 20 題 L2、最大兩次備援替換及點擊放大時的圖片請求數與傳輸量。不得以導入 SW 或內嵌圖片解決，因會直接衝突既有架構限制。 |
| **Medium** | **`<100` 與 A9 的 `≥3000` 是兩套沒有關係的品質門檻。** 前端可在 101 鍵時正常開局，但 CI 規格認為低於 3000 是紅燈。 | 資料更新時會出現「測試判定不可發布，但線上程式仍默默接受」的雙重語意，難以判斷哪一個是產品底線。 | 分開命名：目前資料集回歸門檻、最低可開局門檻、最低教育多樣性門檻；各自說明由 CI、前端或人工發布 gate 負責。不得修改建置管線或 pool schema。 |
| **Medium** | **D13 把文字相似一律視為無從分辨，但 L2 實際選的是圖片，不是相似文字；其風險理由主要適用 L1。** | 若候選過度排除，後續可能為了湊題而增加放寬階段，反而使演算法複雜化；相似藥名也可能本來就是重要教育區辨點。 | 保留安全優先原則，但分別寫明 L1 與 L2 的威脅路徑。若 L2 仍沿用，應明確定義為產品取捨，而不是以「使用者無從分辨文字」作為錯誤因果。 |
| **Low** | **最難回頭的決策不是索引形式，而是「L2 = 同形同色、靠照片刻字辨認」。** 現在風險表把它寫成日後可再加嚴的普通參數。 | 改成要求顏色不同會改變學習目標、難度與所有 F2/A9 基準，不只是調參。 | 將 D12 標成需在動工前通過照片可辨識 gate 的產品決策；未通過時先回到規格審議，不要把它當上線後調整項。 |

# 區塊 3：驗證策略缺口

## 3.1 跨條件缺口

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | **沒有任何驗收直接證明「題幹、正解 Item、顯示圖片、`answerIdx`、作答判定、檢討正解」全鏈路指向同一紀錄。** | 所有單元測試都可全綠，但 DOM 放錯圖片或 index 錯一格；這正是專案第三高風險。 | 新增全鏈路不變量驗收：對 L1/L2 的具名題目快照，逐格核對顯示資產身分與 option Item；`options[answerIdx]` 必須是題幹所屬正解紀錄；作答與檢討必須引用同一快照。這是既有正確配對要求的驗證，不是新增功能。 |
| **High** | **沒有三級最小 end-to-end 作答驗收。** C7 只測選級，C8–C11 集中在 L2 資源，沒有證明 L1 點選、L2 點圖、L3 輸入都能首次鎖定、重複提交不重複計分。 | 渲染、事件與 engine 可各自測過，但級別分派接錯仍會靜默失效。 | 每級至少一個完整回合案例：開始、作答、LOCKED、下一題、完成、分數、檢討；另含錯答、提示及重複事件。 |
| **High** | **spares 的生成條件幾乎沒有 engine 驗收。** A8–A13 多半只談四個正式選項。 | 正式選項全合法，但第一次圖片失敗換入備援後即可產生重複答案、D13 衝突或相同 L2key。 | 所有 L2 choice property tests 應同時驗證正式誘答、兩個備援，以及任一合法替換序列後的目前四格。 |
| **Medium** | **人工檢查與自動斷言界線不清。** C8 寫「DOM 斷言或人工」、C12 寫「可辨刻字」，沒有指定證據。 | 最容易退化成開發者目視一次即打勾，無法重現，也無法防回歸。 | 每條指定證據類型：可自動化的 DOM/尺寸/狀態必須自動；照片可辨識使用固定分層樣本、viewport、縮放狀態與記錄表進行人工 gate。 |

## 3.2 A8–A17：逐條弱化攻擊

| 嚴重度 | 問題：可讓測試通過的弱化實作 | 為什麼現在不修之後會更貴 | 建議修法：堵死弱化版本的斷言 |
|---|---|---|---|
| **High — A8** | `buildChoices` 對每個 ans 都回傳任意四筆甚至重複筆，只要不拋錯就能得到「成功率 100%」。若每鍵只測第一筆，也能隱藏同鍵其他可抽紀錄失敗。單一 seed 還可隱藏貪婪挑選的死路。 | A8 會提供錯誤的全題庫安全感，直到線上抽到未測紀錄或不同 RNG 路徑。 | 先定義答案鍵與紀錄的掃描單位；每個輸出斷言 option 數、H1–H4、L1 形色不相交、D13、正解身分及輸入/index 未被改動。若成功不應依 RNG，至少使用能迫使候選首尾及衝突候選先被挑到的多組 RNG 序列。 |
| **High — A9** | 實作可直接放寬到「任意同形」甚至任意圖片，只要湊出 ≥3000，且讓 `L2key` 形式上不同即可。另一弱化是嚴格階段壞掉，但全部靠放寬仍達 3000；A9 看不出來。 | 會把 L2 靜默退化成 L1，且 F2 的已知 3009 嚴格覆蓋完全失去回歸價值。 | 分別計數嚴格階段與放寬後階段：嚴格結果不得低於已批准基準容忍值，放寬後只能增加；對每題斷言形狀完全相同、嚴格階段顏色完全相同、放寬階段顏色至少相交、四格及所有備援 L2key 兩兩相異。 |
| **Medium — A10** | 只用幾個 fixture 測正解對單一誘答，production `buildChoices` 可能根本沒套用該 predicate；也沒測多色集合的「任一相同即排除」。 | 真實題庫的複合顏色與形狀最容易漏掉。 | 對 A8 的每個實際輸出逐一驗證；具名反例至少包含：完全相同、部分顏色相交、多形狀部分相交、空集合，以及形狀不交但顏色相交。任一相交都必須拒絕。 |
| **High — A11** | 單獨測 `editDistance` fixture 即可通過，但生成器仍可把碰撞選進同題；或只檢查每個誘答與正解，漏掉誘答彼此及備援。也可讓具名案例被硬編排除。 | 線上仍會出現近似選項，而測試名稱看起來已覆蓋 D13。 | 同時測 comparator 單元性質與 `buildChoices` 整合性質；對每一正式選項、備援、替換後四格做全 pair 檢查。反例類別指名：距離 0、1、2；短名/長名；單向前綴、反向前綴、只在中間包含但非前綴；空白差異。 |
| **High — A12** | 固定回傳同一份 20 題可以「固定 seed 可重現」；只比較正解鍵也能隱藏 options、spares、answerIdx 不可重現。H2 可只排除上一題而不是整卷。 | 之後無法重現使用者題卷，且跨題洩題仍可能存在。 | 相同 seed 應對完整深層題卷快照一致，包括紀錄身分、選項順序、spares、answerIdx；至少兩個指定不同 seed 應得到不同題卷。對每題的所有正式/備援誘答，與整卷除本題外的正解集合取交集必須為空；20 個正解也須兩兩相異。 |
| **High — A13** | 實作可不用 RNG，而以題號循環放在 0、1、2、3；分布比仍通過。更糟的是 `answerIdx` 分布正常，但實際正解 Item 沒放在該 index。 | 測試會宣稱「已洗牌」，實際上位置可預測或判定錯位。 | 每題先斷言 `options[answerIdx]` 的紀錄身分就是正解；以可控制 RNG 邊界輸出驗證各 permutation 路徑，而非只看統計。500 題固定 seed 分布可保留為補充；另驗證不同題號本身不能決定位置。 |
| **Medium — A14** | 只測 `pickedIdx = null/-1/4` 即可通過；`NaN`、`Infinity`、字串 `"1"`、小數、物件或無效 `answerIdx` 仍可能被 coercion 判對。 | UI 資料型別或 DOM dataset 改變時會出現誤判為對。 | 指名反例：`undefined`、`null`、`NaN`、±`Infinity`、負數、4、1.5、數字字串、布林值、物件；無效 `answerIdx` 也一律 false。合法案例只接受範圍內整數且嚴格相等，回傳值必須是 boolean。 |
| **High — A15** | `pickEliminated` 可每次回傳不同誘答；只要 transition 第二次不扣分，A15 字面仍通過。它也可能刪到已失敗/已排除格，或回傳越界。 | UI 會顯示多個排除格、提示狀態與分數脫鉤。 | 分拆驗收：純挑選函式須回傳範圍內、存在、未排除且非正解的格；同一 hint 事件只決定一次並持久保存該 index。狀態機測試連續兩次 hint，確認點數只由 1 降至 0.5 一次、排除格仍只有一個，LOCKED 後 hint 無效果。 |
| **High — A16** | 只測 20 題全對且未提示，可讓錯答、hinted、void 分母或空卷計算全錯仍通過。「三級公式相同」也可只是回傳同一硬編數字。 | 成績頁與 PNG 會在混合真實題卷才出錯，且可能誤導能力判讀。 | 先解決 L2 hint 基線定義；再以明確矩陣驗證 correct=1、hinted correct=0.5、wrong=0、void 不進分子/分母、混合題、全部 void/中止的既有語意。三級使用相同題目結果時 score 必須相同，只有已定義的 baseline metadata 不同。 |
| **High — A17** | 只檢查 pool 內既有 `content_hash` 字串未變，實作者可改內容但忘記更新 hash；小型 gold set 也可被特判。甚至能修改 build tool 而本次測試仍綠。 | 這會讓「未動答案鍵」成為無效保證，直到下次月更才爆發大規模漂移。 | 驗收改成 `data/pool.json` 檔案 bytes 或由內容重新計算的獨立 digest 與核准基線相同；`normalize()` 使用凍結且涵蓋標點、空白、大小寫、Unicode、空值的 golden corpus 逐字比較。另以變更範圍檢查確認 `tools/*`、pool 及 `normalize()` 所在區段沒有本次 diff；此作法與「不得重跑 build:pool」相容。 |

## 3.3 C7–C14：逐條弱化攻擊

| 嚴重度 | 問題：可讓測試通過的弱化實作 | 為什麼現在不修之後會更貴 | 建議修法：堵死弱化版本的斷言 |
|---|---|---|---|
| **High — C7** | 只替按鈕加 `disabled` 外觀即可；直接觸發 handler、Enter 鍵或殘留全域 level 仍能開始。也可能第二回合自動沿用上一級。 | 會產生成績卡級別與使用者預期不符，且只有特定導航路徑才出現。 | 驗證首次與第二回合進入 start 都沒有選級；滑鼠、鍵盤及直接觸發開始事件都不得建立 quiz。選級後只啟用一次，建立的 QuizSession level 必須等於畫面選擇。 |
| **High — C8** | 把 `#qFeatures` 設為 `display:none` 即可通過人工目視，但特徵仍可能存在於可及性名稱、`alt`、`title`、放大 modal 或其他隱藏文字；反之只查 DOM 不含特定標籤，畫面仍可由其他元素洩露內容。 | 後續重構 CSS 或輔助屬性時會重新送分而不被察覺。 | 在 L2 題目與放大畫面的可見文字及 accessibility tree 中，斷言不含該題 shape/color/score/mark1/mark2/size 的實際值；同時正向斷言只呈現允許的 `full + zh`。避免只找固定中文欄名。 |
| **High — C9** | 觸發 404 後只把格子換成任意成功圖片即可通過「題目續行」；新圖可能仍是同一 ans、違反 L2key、與 metadata 不一致，甚至只改 DOM `src` 沒改判定快照。 | 第一次真實資源錯誤就可能造成圖片與答案錯配。 | 斷言替換前後格位固定、Item identity 與 `src` 同步更新、新圖成功載入、正式四格重新滿足 H1–H3/L2key、正解及其他格不變、分母不變。再含兩格同時失敗、替換圖失敗及兩個備援耗盡案例。 |
| **High — C10** | UI 可直接跳下一題，看似遞補，但原題仍留在分母或已先計成錯；也可能遞補到重複正解或沒有維持 20 個有效題。 | 成績會靜默失真，且回合顯示題數仍可能看似正常。 | 核對失敗題進入 `void`、分子分母均不含它、替補題正解不重複、最終恰有 20 個有效題；同一錯誤事件重送不得再次增加 void 或再遞補。另保留 `>3` 中止的既有回歸。 |
| **High — C11** | 只測「換到下一題後的舊事件」仍不足；同一題同一格換備援後，舊 `src` 的遲到事件仍可把新圖再次換掉。只比對題號和格 index 會通過現有案例。 | 真實瀏覽器最常出現的是同一 DOM `<img>` 改 `src` 後舊請求回報，會誤傷目前選項。 | 反例至少包含：已換題、同題同格已換 `src`、同題其他格、LOCKED 後事件。事件只有在題目 token、格位 token、目前資產 identity/src 全部相符時才可生效；所有遲到事件前後的題目快照及分數必須完全不變。 |
| **Medium — C12** | 只斷言 viewport 沒有 body scrollbar，內層 grid 仍可裁切；按鈕 CSS 高度 44px，但實際 hit area 受縮放或重疊影響。「可辨刻字」可由開發者主觀打勾。 | 手機完成後才修通常會連動四宮格、放大及提示標示。 | 自動驗證 document 與所有主要容器的 scroll width、四格 bounding box 位於 viewport、實際可點區域至少 44×44。照片可辨識改用固定 375px 截圖與具名分層樣本人工審查，並驗證放大後可回到原題且不改狀態。 |
| **High — C13** | 頁面 DOM 上有級別和基線即可宣稱「畫面上印有」，但下載 PNG 內可能沒有；或 Canvas 呼叫了文字 API但文字被裁切、透明、畫在畫布外。只測可 decode 也不證明檔名或內容。 | 成績卡是離開頁面後唯一可見的上下文，漏印會放大分數誤讀風險。 | 對三個級別及至少兩種分數產生實際 blob，驗證 MIME、非空、可解碼、合理尺寸與檔名；以可重現的 Canvas 繪製紀錄或成品視覺/OCR 檢查，確認級別、分數及正確 baseline 位於畫布可視範圍。另確認未嘗試繪製任何跨域藥品圖片，維持既有 CORS 限制。 |
| **Medium — C14** | 在熱快取、localhost、只算 HTML，或在 pool 載入前停止量測，就能低於 3MB；`Content-Length` 也不等於實際冷快取傳輸量。 | 新增字型、重複載入或初始化請求可能在線上才超標。 | 固定以關閉快取的瀏覽器網路 trace，從 navigation 到「可開始測驗」狀態，累加所有非題目圖片資源的 transfer bytes；列出包含 HTML/CSS/JS/font/pool、排除項目及 GitHub Pages 壓縮環境。另立題目圖片流量驗收，因 C14 本身不能覆蓋 200MB 限制。 |

# 區塊 4：更簡單的替代方案

整體「三級共用 pool、誘答執行期產生、不改 normalize」**不算 over-engineering**。主要過度複雜處在「逐格備援替換」及把固定 chance 塞入計分核心。

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | **逐題抽取、失敗再補抽、同時維持 H2 是不必要的回溯複雜度。** | 寫完才發現全域排除被後補正解破壞，會重做整個生成流程。 | 採更簡單的兩階段規格：先建立各級可用答案鍵集合並等機率選定 20 個正解，再用完整正解集合組裝選項。若任何題無法組裝，整卷重新選取或從已知可用集合替換，最後做一次全卷不變量驗證。pool 與管線均不需改。 |
| **High** | **D15 的「同一格即時替換」帶來格位、spare、提示、遲到事件五者耦合。** | 這是 app.js 最容易膨脹且最難測的部分。 | 可考慮更簡單的「預備完整替補題」：任一誘答圖失敗時，在使用者尚未作答且題目未 ready 的前提下，整題換成另一份已組好的題目，而不是局部換格。正解圖仍作廢；對使用者同樣避免三選一與錯誤計分，但 race surface 較小。需由使用者決定是否接受題幹在載入期被替換。 |
| **Medium** | **`scoreQuiz()` 新增固定 `chance` 只為顯示文案，會把級別 UI metadata 耦合進既有計分核心。** | 後續若修正提示後基線，函式介面和所有呼叫端都要再次改。 | 若採「未使用提示的四選一基線」，把基線定義為 level 的展示 metadata，既有 score 計算完全不動；欄位名稱及文案不可宣稱是本回合實際隨機期望值。若一定要顯示「淨高於基線」，則改採依作答歷程計算，不能使用固定 metadata。 |
| **Medium** | **L2 提示同時增加 UI 狀態、排除格、計分基線歧義及圖片替換 race。** | 它是多個複雜度來源的共同交點，但不是 L2 核心「名稱→圖片」目標。 | 最簡單替代是 L2 與 L1 一樣不提供提示；L3 保留首字母提示。這會改動已寫明的功能，因此屬產品取捨，不能由實作者自行採用，但值得在動工前決定。 |
| **Blocker** | **若不先驗證照片可辨識，直接完成 engine 與 UI 是最高成本路徑。** | 一旦人工試用證明刻字多數不可讀，所有 L2 演算法與驗收基準都會失去意義。 | 先做不涉及程式碼的分層照片審查：用規格中的 2×2、約 160px 與放大條件，人工驗證一批嚴格同形同色題。通過後才固定 D12；未通過則先改誘答原則。 |
| **Medium** | **目前同時把「可用性判斷」與「隨機選擇」塞進 `buildChoices`，使全題庫驗證必須依賴 RNG。** | 隨機貪婪路徑可能把本來可組題的答案鍵判成不可用，產生難重現失敗。 | 規格層分離兩個性質：先判定候選集合是否存在合法組合，再從合法候選中隨機選擇。驗收分別證明 eligibility 與 shuffle；不需要把誘答寫入 pool，也不觸碰建置管線。 |

最小動工前修訂集合應包含：

- 定義 answer key → record → image → option → review 的單一身分鏈。
- 定義 v3 Question/QuizSession 契約及 H2 的整卷生成交易。
- 解決 L2 提示後 baseline 不是固定 25 的矛盾。
- 先以實際照片完成 L2 可辨識 gate。
- 將 A8–A17、C7–C14 改成上述「性質斷言」，尤其補上 spares、替換後不變量及全鏈路圖片配對驗證。
