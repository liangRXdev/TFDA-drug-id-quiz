結論：v5.0 尚不宜直接進入實作。主要有 4 個 Blocker：

- D37 的三分類無法容納 Q3，資料模型自相矛盾。
- D34 沒有完整 wire format／完整性檢查，A40 的「任意中段位元竄改必須失敗」在技術上不可保證。
- D38 把「eligible key 數」誤當成「一定組得出符合 H2 的題卷」。
- U2、U3 仍未決，但直接決定 URL 格式與輸入解析契約；現在實作很可能整段重寫。

以下均為規格覆審；未修改任何檔案。

# 1. 需求與邊界缺漏

## 1.1 Q3 沒有對應的未命中類別

- **嚴重度：Blocker**
- **問題：** `excluded.json.stage` 明定含 Q1–Q5，但 D37 的三類只映射 Q1、Q2/Q4/Q5、來源不存在，完全沒有 Q3「答案鍵不足 3 字元」。A44 卻要求所有輸入恰好落入四個顯示集合之一。
- **為什麼現在不修之後會更貴：** 管線、前端統計、下載清單及測試會各自發明不同的 Q3 歸類，最後只能改資料模型及 UI 文案。
- **建議修法：** 在規格中明定 Q3 的顯示歸屬；若併入第二類，類名必須擴成能如實涵蓋「品名不適合作答」的名稱。A44 加入一筆 Q3 專屬案例，斷言其精確分類。

## 1.2 一個 id 有多筆來源列時的裁決未定義

- **嚴重度：High**
- **問題：** B10 以「來源去重後 id」為母集合，但沒有定義同一 id 多列、且各列通過不同 Q stage 時如何裁決。尤其可能出現一列存活、另一列 Q2/Q4 失敗。
- **為什麼現在不修之後會更貴：** `pool`／`excluded` 可能同時含同一 id，或結果依來源列順序改變，直接破壞互斥與冪等。
- **建議修法：** 明定 id 聚合規則及 precedence：至少要說明「任一列存活時是否一律算 matched」、全部淘汰時如何選唯一 stage，以及輸入順序不得影響結果。B10 加入衝突重複列。

## 1.3 「同時符合多個 excluded stage」與單一 stage 模型衝突

- **嚴重度：High**
- **問題：** 現行 Q1→Q5 是循序 filter，實際能記錄的是首次失敗；`{id, stage}` 也只能存一個 stage。A44 卻要求「同時符合多個 stage」的案例，但未定義優先順序。
- **為什麼現在不修之後會更貴：** 管線可能記首次失敗，前端分類函式卻自行重算成其他原因，兩層不一致。
- **建議修法：** 明定 `stage` 是「首次淘汰 stage」，並固定 Q1→Q5 precedence；或改成多原因模型。若維持單值，A44 應斷言精確的首次失敗 stage。

## 1.4 上傳／貼上內容如何切成 id 未定義

- **嚴重度：Blocker**
- **問題：** U3 暫定兩者都做，但規格沒有檔案格式、編碼、欄名、分隔符、引號、BOM、空列、混合說明文字及一列多欄時的解析規則。D35 只定義單一 token 正規化，沒有定義 tokenization。
- **為什麼現在不修之後會更貴：** UI、解析器及驗收 fixture 都會綁死不同假設；取得真實院內檔案後很可能整段重寫。
- **建議修法：** 在 U3 結案前，至少指定本版接受的輸入契約。例如「純文字，每行一個 id」是否為唯一正式格式；若接受 CSV，須明定欄位選擇與解析失敗行為。這是既有上傳目標的必要定義，不是新增功能。

## 1.5 連結究竟編碼「原始清單」還是「目前命中清單」未定義

- **嚴重度：High**
- **問題：** D34 稱編碼院內清單，5.2 卻先三方比對再產連結。若只編碼 matched，月更後新納入 pool 的 id 永遠無法恢復；若編碼全部正規化 id，codec 必須支援目前 pool 外的合法 id。
- **為什麼現在不修之後會更貴：** 會同時影響 codec 可接受範圍、URL 長度、D41 降級／恢復及 localStorage schema。
- **建議修法：** 明定連結及 storage 保存的是哪個集合。為符合 D41「不清除清單」，應再明定品項重新出現時是否自動恢復。

## 1.6 `?v=` 沒有語意

- **嚴重度：High**
- **問題：** URL 帶 `v=<source_version>`，但未說明與目前 pool 相同、較舊、較新、缺失、格式錯誤時各做什麼。D34 又宣稱編碼與 pool 版本無關。
- **為什麼現在不修之後會更貴：** 有人會把 `v` 當阻斷條件，有人只顯示警告；連結相容性及 D41 行為會分歧。
- **建議修法：** 定義 `v` 是資訊／警告欄位還是驗證欄位，且其文字不得直接取 URL。若沒有任何決策用途，刪除它可減少狀態。

## 1.7 啟動流程缺乏原子發布點

- **嚴重度：High**
- **問題：** 有效 fx 的流程包含解碼、下載 pool、比對、計算 eligibility、寫 storage、更新記憶體及移除 URL。這些步驟任一失敗時，哪些可以提交尚未定義。
- **為什麼現在不修之後會更貴：** 容易出現 URL 已移除但清單未保存、storage 是 B 而畫面仍是 A，或錯誤連結污染現有狀態。
- **建議修法：** 規格化單一 commit point：所有驗證及索引建構成功後，才一次發布記憶體狀態、持久化及消費 URL；任一步失敗時既有狀態位元組不變。

## 1.8 localStorage formulary schema 未定義

- **嚴重度：High**
- **問題：** 未定義保存原始 id、正規化 id、encoded payload、版本、checksum、建立時 source version，亦未定義 schema 不相容或 JSON 損毀時的唯讀降級。
- **為什麼現在不修之後會更貴：** D41、codec 升版及讀取失敗紀律都會迫使資料遷移；不同實作者可能在讀取時偷偷覆寫修復。
- **建議修法：** 明定版本化 schema、必要欄位、合法性條件，以及「讀取／驗證失敗不得 mutation」的行為。

## 1.9 不同院內清單共用 `records-fx`

- **嚴重度：High**
- **問題：** D40 只把院內版與通用版分開，卻讓不同醫院清單、換清單前後及月更縮水前後共享同一最佳紀錄。D39 又明確認為不同卷長不可比。
- **為什麼現在不修之後會更貴：** 一旦寫入單一 schema，之後要改成按 formulary identity 分區就涉及遷移；畫面會顯示來自完全不同題庫的最佳成績。
- **建議修法：** 規格需選定：院內紀錄按清單 fingerprint 分區、清單改變時視為不同基準，或院內版本批完全不寫最佳紀錄。後者最簡單。

## 1.10 切回通用版的清除範圍不完整

- **嚴重度：Medium**
- **問題：** 只說「主動切回」，未定義應移除哪個 key、是否保留 `records-fx`、失敗時畫面與 storage 誰優先，以及不得觸碰其他同源 key。
- **為什麼現在不修之後會更貴：** UI 流程完成後才會發現無法寫出可證偽的 storage 驗收。
- **建議修法：** 明定只對 formulary key 做精確 `removeItem`；records 是否保留另作明確決策。移除失敗時不得宣稱已永久切回。

## 1.11 外部資料取得失敗路徑不完整

- **嚴重度：Medium**
- **問題：** 未定義 `pool.json`／`excluded.json` 非 200、JSON 損毀、schema 錯誤、版本不一致、其中一檔成功另一檔失敗時，通用測驗與產連結頁各自如何降級。
- **為什麼現在不修之後會更貴：** 很容易為了讓 UI 可用而採用半套資料，產生錯誤未命中分類。
- **建議修法：** 產連結功能需兩檔成對驗證後才發布；任何一檔失敗不得產連結。若既有通用版只需 pool，應明定它不因 excluded 失敗而失效。

## 1.12 重入與非同步競態未定義

- **嚴重度：Medium**
- **問題：** 快速重複產連結、連點級別、載入 fx 時切回通用版，以及較舊非同步結果晚於較新操作完成，皆沒有 winner 規則。
- **為什麼現在不修之後會更貴：** 後補 guard 會散落在每個入口，容易重現既有 retry 流程曾處理過的「舊 Promise 搶回畫面」問題。
- **建議修法：** 定義一次只能有一個 active operation；新操作取消／使舊結果失效，且只有當前 operation 可以 commit。
- **[新增需求]：** 若要多分頁即時同步，另需 `storage` event 規格；目前目標不要求，可明確排除，接受 last-writer-wins。

## 1.13 重複、空值及超大 `fx` 的解析界線未定義

- **嚴重度：Medium**
- **問題：** 未涵蓋空 `?fx=`、多個 fx、重複 v、base64 padding、大小寫、超大宣稱筆數、超長 varint、重複 id、非遞增 delta。
- **為什麼現在不修之後會更貴：** decoder 會變成實際的格式規格；之後收緊可能使已分享連結失效。
- **建議修法：** 在 D34 定義 canonical grammar、資源上限及 fail-closed 條件；同一集合只允許一個 canonical encoding。

## 1.14 C43 的涵蓋數字語意不夠精確

- **嚴重度：Medium**
- **問題：** 「涵蓋 N 品項」可能是輸入 id、matched items、eligible answer keys 或本級可出題 keys；四者不同。
- **為什麼現在不修之後會更貴：** 次要風險正是虛假完成感，模糊數字會讓 UI 以較大的 matched item 數暗示使用者都可實際練到。
- **建議修法：** 每個數字固定名稱與母集合，例如「院內清單命中 N 品項；本級可出題 K 個答案鍵」。不得用 N 代替 K。

# 2. 架構風險

## 2.1 D38 的可用性指標不足以保證能出卷

- **嚴重度：Blocker**
- **問題：** `eligibleKeys.size >= n` 只是逐鍵局部可出題，不代表能組出一卷同時滿足 H2 與誘答資源限制。現有 `drawLeveledQuiz` 本身還要求額外答案鍵並可能回 `QUIZ_ASSEMBLY_FAILED`。
- **為什麼現在不修之後會更貴：** UI 會宣稱級別可用，開始後才失敗；若以重複題或跨子集誘答救場，正好破壞核心病安約束。
- **建議修法：** 將「級別可用」定義成能成功構造指定卷長且通過全部 invariant，而非只看 `.size`。門檻數仍可作快速前置條件，但不能是最終可用性證據。

## 2.2 A40 與 D34 的格式能力矛盾

- **嚴重度：Blocker**
- **問題：** 純 delta＋varint＋base64url 沒有 checksum。任意中段 bit flip 很可能仍是合法 varint，只會解成另一個合法 id，decoder 無法知道資料被竄改。
- **為什麼現在不修之後會更貴：** codec 一旦發布就是永久 wire format；後補完整性欄位需版本分流及相容 decoder。
- **建議修法：** D34 必須先定義格式版本、magic/count、prefix table 版本、canonical varint 與完整性檢查。否則 A40 應縮成只保證「結構上不可解析的損毀 fail」，不能宣稱所有 bit flip 都會失敗。

## 2.3 11 種前綴表未版本化

- **嚴重度：High**
- **問題：** 未列出完整前綴、索引順序、canonical 中文字形及未來新增前綴的處理。
- **為什麼現在不修之後會更貴：** 調整表順序就會靜默把舊連結解成不同藥證，風險與被否決的 bitmap 相同。
- **建議修法：** 把 prefix table 及 codec version 寫成不可變 wire contract；新增前綴只能升格式版本，不得重排既有 index。

## 2.4 `source_version` 不足以識別兩檔是否成對

- **嚴重度：High**
- **問題：** 同日來源可重編；現有 pool 已有 `content_hash`。只比較日期不能防止同版本、不同內容的 pool/excluded 配對。
- **為什麼現在不修之後會更貴：** 教學端可能錯誤解釋未命中原因；之後才加 pair identity 又需改兩檔 schema。
- **建議修法：** 兩檔共同攜帶同一不可混淆的 source fingerprint／content hash，配對驗證以 fingerprint 為準，日期只供顯示。

## 2.5 「兩個檔案都不得寫出」缺乏可實現的交易邊界

- **嚴重度：High**
- **問題：** 單純先在記憶體驗完再依序寫兩檔，第二次寫入失敗仍會留下第一檔。B12 的要求比目前資料流所定義的原子性更強。
- **為什麼現在不修之後會更貴：** 管線完成後才補 staging，會牽動 build、verify、image 更新及 workflow 發布順序。
- **建議修法：** 規格應把原子性定義在 GitHub Actions 發布層：先在隔離 staging 產生並驗證整組，再一次提交成對產物；失敗時工作樹的既有正式產物位元組不變。相容零後端限制。

## 2.6 D40 是最難回頭的資料模型決策之一

- **嚴重度：High**
- **問題：** 單一 `records-fx` 沒有清單 identity，無法區分不同題庫基準。
- **為什麼現在不修之後會更貴：** 已寫入的紀錄無法可靠反推屬於哪一份清單。
- **建議修法：** 在首次發布前決定紀錄是否完全停用，或以 canonical formulary fingerprint 作 namespace。

## 2.7 D42 未決使 D34 無法定稿

- **嚴重度：Blocker**
- **問題：** 1800 base64 字元是 payload 還是完整 URL 未說明；「警告但仍產出」也沒有界定何時連結被視為不可分享。U2 fallback 會反過來決定 codec 是否值得存在。
- **為什麼現在不修之後會更貴：** 寫完 binary codec 後若最後採檔案 fallback，主要複雜度可能沒有價值。
- **建議修法：** 先決定本版的硬上限與超限結果。若本版核心是可分享連結，超限時應明確「不保證可用」或拒絕，而不是只警告後仍宣稱產生成功。

## 2.8 未違反既有平台限制，但需防止錯誤補救

- **嚴重度：Low**
- **問題：** 目前提案本身可在零後端、零依賴、無 build step 前端下完成；真正風險是為了解決 codec、layout 或原子發布而臨時引入後端／jsdom／資料 SW cache。
- **為什麼現在不修之後會更貴：** 會破壞已明定的維護及版本一致性邊界。
- **建議修法：** 規格明列相容解法：codec 使用純函式、CSS 走靜態契約＋人工留檔、管線原子性放在 Actions staging、pool/images 維持不進 SW。

# 3. 驗證策略缺口

以下逐條回答「什麼弱化實作仍會通過」。

## A36

- **嚴重度：Medium**
- **問題：** 可只 hardcode 指定的 5 組反例；其他 22 組及完整 prefix 表仍可錯。
- **為什麼現在不修之後會更貴：** prefix 錯配會直接造成 A 藥照片配 B 藥名。
- **建議修法：** 除至少 5 組明列例外外，對完整已知撞號集合逐組斷言 canonical id、彼此不等及各自唯一命中；另驗 prefix table 中每種前綴。

## A37

- **嚴重度：Medium**
- **問題：** 每類只 hardcode 一個正反例即可通過；組合輸入、重複正規化及兩個不同合法 id 的 collision 未驗。
- **為什麼現在不修之後會更貴：** 實際貼上資料通常同時含全形、空白與缺第／號。
- **建議修法：** 每類指定反例類別與預期 canonical 值，增加組合案例、冪等性 `N(N(x))=N(x)`、合法 id 不碰撞及未知前綴拒絕。

## A38

- **嚴重度：High**
- **問題：** encode/decode 共享同一份錯誤 prefix 表仍可完美 round-trip；也可只支援目前 pool 內 id。
- **為什麼現在不修之後會更貴：** 舊連結跨版本解碼時才會暴露。
- **建議修法：** 加入獨立 golden vectors，逐一指定輸入集合、精確 encoded bytes/string 與 decoded canonical ids；案例須含目前 pool 外但格式合法的 id，以及 codec version。

## A39

- **嚴重度：Low**
- **問題：** 可只對測試那一組集合回固定字串。
- **為什麼現在不修之後會更貴：** 非 canonical encoding 會讓 fingerprint、紀錄分區及連結去重失效。
- **建議修法：** 對多組含跨前綴、重複輸入及邊界號碼的集合做 permutation；並與 A38 golden encoding 合併驗證。

## A40

- **嚴重度：Blocker**
- **問題：** 可針對四個 fixture hardcode 拒絕；且沒有 checksum 時，合法 bit flip 根本無法保證被偵測。
- **為什麼現在不修之後會更貴：** 測試會製造最危險的假綠燈。
- **建議修法：** 先修 D34 格式。其後對每個 byte/多個 bit 位置系統性竄改，斷言完整性失敗；另驗非 canonical varint、overflow、超額 count、重複／倒退 delta，且錯誤前回傳值必須完全不存在。

## A41

- **嚴重度：High**
- **問題：** 20 次隨機抽樣可剛好沒抽到洩漏品項；空卷也可能讓逐題斷言 vacuous pass。
- **為什麼現在不修之後會更貴：** 偶發跨院內誘答會直接教錯使用者。
- **建議修法：** 使用可控制 RNG 的敵意資料，強迫抽到 pool-only sentinel；每卷先斷言成功且長度正確，再逐題驗正解 item、所有 option item、spare item 均屬子集，並驗全部 invariants。

## A42

- **嚴重度：High**
- **問題：** 可讓 availability 函式只對 fixture size 回預期標籤，完全不證明能出卷。
- **為什麼現在不修之後會更貴：** UI 顯示可用，實際開始才組卷失敗。
- **建議修法：** 以真實 `buildIndex` 產生精確 9/10/19/20 eligible keys；逐一斷言狀態、卷長，且所有標記可用案例均實際成功出卷並通過 invariants。三個 level 分別驗。

## A43

- **嚴重度：High**
- **問題：** 可回傳 14 個正解 key，但 options 重複、跨子集或違反 H2；目前只驗正解集合。
- **為什麼現在不修之後會更貴：** 短卷才是最容易耗盡誘答資源的區域。
- **建議修法：** 除長度與正解集合外，驗全部 options/spares 封閉於子集、每題選項合法，並要求 `validateQuizInvariants()` 為空。

## A44

- **嚴重度：High**
- **問題：** 可把所有 unmatched 都錯分到同一類，總和與互斥仍成立；Q3 也未測。
- **為什麼現在不修之後會更貴：** 使用者會得到錯誤的排除原因。
- **建議修法：** 對 matched、Q1、Q2、Q3、Q4、Q5、來源不存在逐筆斷言精確 membership；加入重複 id 與多重失敗 precedence。修正顯示分類後再保留總和封閉性。

## A45

- **嚴重度：Medium**
- **問題：** 規格寫「三種輸入」但沒有列出三種；只要不拋例外且回四個空集合即可通過。
- **為什麼現在不修之後會更貴：** 實作者與測試作者會各自猜測第三種案例。
- **建議修法：** 明列三種輸入及精確結果，例如完全空字串、只有空白／分隔符、同一合法 id 重複多次；逐一斷言去重後集合與各分類 membership，不只總和。

## B10

- **嚴重度：High**
- **問題：** 把所有來源 id 都塞進 excluded、pool 留空，也能滿足互斥與聯集；用同一錯誤 parser 產生母集合也會自洽。
- **為什麼現在不修之後會更貴：** 管線可全綠但正式題庫消失。
- **建議修法：** fixture 必須包含每個 Q stage 與已知 survivor，逐筆驗精確輸出集合及 stage；另驗來源列數、去重規則、既有 pool 數量 gate 與 id 不可空。

## B11

- **嚴重度：Medium**
- **問題：** 可只拒絕指定的未知字串，卻放行缺 stage、null、陣列、大小寫變體或額外空白。
- **為什麼現在不修之後會更貴：** 前端分類遇到非封閉值域會落入錯誤 fallback。
- **建議修法：** 對未知值、缺欄位、null、非字串、錯誤大小寫逐一驗 fail；同時加入 Q1–Q5 全部合法的正面 fixture。

## B12

- **嚴重度：High**
- **問題：** fixture 可因其他 schema 錯誤而 fail；「不得寫出任何檔案」也偵測不到先寫後回滾。
- **為什麼現在不修之後會更貴：** 測試宣稱原子發布，實際只證明 process exit 非零。
- **建議修法：** fixture 除版本外完全合法，斷言錯誤原因；預先放置 sentinel 正式檔，失敗後兩檔位元組完全不變。成功案例再驗兩檔 fingerprint 相同。

## C40

- **嚴重度：Medium**
- **問題：** UI 可 hardcode 四個 fixture 數字；下載檔只要筆數相同，即使內容全錯也會通過。
- **為什麼現在不修之後會更貴：** 統計看似正確，實際清單無法追查。
- **建議修法：** 逐類斷言精確 id 集合；把下載內容重新解析後，斷言 canonical ids、類別及順序契約與畫面資料完全一致，而非只比筆數。

## C41

- **嚴重度：High**
- **問題：** 空卷的聯集是空集合，自然是 matched 子集；10 次隨機也可能漏過污染路徑。
- **為什麼現在不修之後會更貴：** 這條是 D36 的核心跨層保護，假綠燈代價最高。
- **建議修法：** 每卷先驗成功、正確卷長及 invariants；逐題驗正解與所有誘答／spares。使用 pool-only sentinel 與受控 RNG 強迫走可能洩漏的分支。

## C42

- **嚴重度：High**
- **問題：** 只驗 formulary key 仍是 A；實作可改 records、removeItem 其他 key、清空記憶體後再把畫面假裝成 A。
- **為什麼現在不修之後會更貴：** 損毀連結可能破壞既有使用狀態。
- **建議修法：** 對解碼前後的完整記憶體 snapshot、所有相關 storage 位元組與 mutation call log 做相等斷言；錯誤後仍須能從 A 正常出卷。把 `mode` 改成明確的「formulary/general active mode」，避免與既有 quiz/retry mode 混淆。

## C43

- **嚴重度：Medium**
- **問題：** 測試樁無 CSS 可見性，DOM 有文字就可能假裝「可見」；也可顯示錯誤的 N。
- **為什麼現在不修之後會更貴：** 這正是已知的 layout 假綠燈類型。
- **建議修法：** 自動測試只驗答題頁、結算頁皆存在語意節點及精確 N/K 與範圍文案；可見性與換行移到 C51。另加靜態契約，確認節點未被固定 `hidden`／不可及屬性遮蔽。

## C44

- **嚴重度：High**
- **問題：** 可顯示任意「縮水」訊息，題卷甚至為空；「未清除」只看 key 存在，也可能已把原清單覆寫成殘餘集合。
- **為什麼現在不修之後會更貴：** 一旦覆寫，日後品項恢復也無法重新加入。
- **建議修法：** 指定消失 id 與精確 survivors；斷言持久化的原始 canonical formulary 位元組不變、active matched 集合精確縮小、可用性精確轉換，且實際完成一卷。再決定並驗證重新出現時是否恢復。

## C45

- **嚴重度：High**
- **問題：** stub 上的「可見」無證據；程式化入口可偷偷修改 level、啟動 preload、寫 storage 後再返回，最終畫面看似 no-op。
- **為什麼現在不修之後會更貴：** 禁用級別仍可能透過鍵盤、舊事件或直接呼叫啟動。
- **建議修法：** 自動測試驗 semantic disabled 狀態、原因文字、事件入口呼叫前後完整 state/storage/timer/image-load call log 不變；CSS 可見性留給靜態契約及 C51。

## C46

- **嚴重度：High**
- **問題：** 完全不記錄任何成績也可能通過；「短卷後再跑通用較低分」混合了短卷排除與 records 分離，結果不易判讀。
- **為什麼現在不修之後會更貴：** 紀錄功能靜默失效仍會全綠。
- **建議修法：** 先在 `records-fx` 放高低不同的 sentinel，短卷結算後立即斷言該 key 位元組完全不變且無 mutation；另以正常 20 題院內卷證明可合法更新。通用版寫入應由 C47 獨立驗。

## C47

- **嚴重度：High**
- **問題：** 只驗另一個 key 未變；實作可以兩種模式都不寫、或都只寫 `records-fx` 而碰巧測不到。
- **為什麼現在不修之後會更貴：** 成績分離名義存在、實際紀錄路徑缺失。
- **建議修法：** 對每個方向都斷言目標 key 的精確預期更新、非目標 key 位元組不變，以及 mutation call log 只含允許的精確 key。

## C48

- **嚴重度：High**
- **問題：** 只禁止 `setItem`，實作仍可 `removeItem` 或 `clear()`；也未涵蓋 property access 拋錯及不同 key 的讀取失敗。
- **為什麼現在不修之後會更貴：** 會違反專案最重要的同源 storage 紀律。
- **建議修法：** 斷言所有 mutation（set/remove/clear）為零；分別測 localStorage 不存在、property access 拋錯、getItem 拋錯、JSON/schema 錯誤，並覆蓋三個本站 key。

## C49

- **嚴重度：Medium**
- **問題：** 刪掉整個 query string 就能通過「不含 fx」；所謂重整也可能沒有真的重跑 bootstrap。
- **為什麼現在不修之後會更貴：** 會破壞其他 query 參數，或 URL 已消費但清單未成功保存。
- **建議修法：** 指定原 URL 含 fx、v、無關參數及 fragment；成功後只移除規格要求的參數，其他內容精確保留。重新執行完整啟動流程，斷言沒有第二次 formulary mutation。失敗連結是否保留 fx 也須先定義。

## C50

- **嚴重度：High**
- **問題：** 既定 prefix＋number codec 理論上不應解出 `<img…>`；若測試繞過 decoder 注入任意字串，沒驗到真實 URL 路徑。只查最終 `innerHTML` 不含原字串，也抓不到經轉形或進入 attribute 的 payload。
- **為什麼現在不修之後會更貴：** 可能又形成「掃描範圍正確但命中定義錯誤」的假綠燈。
- **建議修法：** 分成兩層：真實 decoder 對非格式字元 fail-closed；分類／下載層的惡意字串只能經 `textContent` 類純文字 sink。測試需監控所有 HTML／attribute／URL sink，不只比對最終 innerHTML；靜態契約掃描完整 URL-to-DOM 路徑，解析失敗即測試失敗。

## C51

- **嚴重度：Medium**
- **問題：** 沒有指定留檔組合、頁面狀態、字型載入狀態及判定證據；只看一張首頁截圖也可宣稱通過。
- **為什麼現在不修之後會更貴：** UI 完成後才發現人工驗收不可重現。
- **建議修法：** 明定最少留檔矩陣：375px 產連結結果頁、答題頁、結算頁、含禁用級別狀態；每張須顯示 viewport、測試資料 N/K 與 verdict。這符合既有「人工瀏覽器留檔」，不需引入任何瀏覽器測試依賴。

# 4. 更簡單的替代方案

## 4.1 取消三類未命中，只保留 matched／unmatched

- **嚴重度：High**
- **問題：** `excluded.json`、Q stage attribution、雙檔配對及多數 B/C 驗收，都是為「解釋為何未命中」服務；核心目標只要求院內子集出題。
- **為什麼現在不修之後會更貴：** 這會新增一條長期資料契約及每月原子發布責任，但不直接降低教錯藥名的核心風險。
- **建議修法：** 最簡版只顯示「可出題／目前題庫未收錄」，並允許下載 unmatched canonical ids。若三類原因對教學藥師確有必要，再保留 D37，但必須先解決 Q3 與 stage precedence。此方案不新增需求，也不碰後端或依賴。

## 4.2 院內版不保存最佳紀錄

- **嚴重度：High**
- **問題：** 為了院內模式新增 `records-fx`，立刻引出清單 identity、月更縮水及不同卷長的可比性問題；個人進度本來又是明列非目標。
- **為什麼現在不修之後會更貴：** 一旦發布無 identity 的紀錄，後續無法可靠遷移。
- **建議修法：** V5 院內版只提供當回合分數，不寫最佳紀錄；保留通用版既有 records 完全不動。V5.1 定義進度／清單 identity 時再一起設計。這是最小且風險最低的方案。

## 4.3 使用較容易審核的版本化文字編碼

- **嚴重度：Medium**
- **問題：** 自訂 binary varint＋base64url 增加 canonicality、截斷、overflow、bit corruption 及 golden-vector 負擔。
- **為什麼現在不修之後會更貴：** wire format 發布後不能任意修正。
- **建議修法：** 可評估版本化的「prefix index＋base36 delta＋明確分隔符＋checksum」文字格式。仍維持純前端、零依賴、與 pool 排序無關，但較容易人工檢查及建立獨立 golden vectors。若實測長度不合格，再保留 binary codec；應以完整 URL 長度比較，不只 payload。

## 4.4 對超限清單直接拒絕，不在 V5 同時做檔案 fallback

- **嚴重度：Medium**
- **問題：** U2 同時考慮可分享 URL 與檔案 fallback，會形成兩套匯入、驗證及分享流程。
- **為什麼現在不修之後會更貴：** fallback 會倍增 C40–C50 的跨層狀態。
- **建議修法：** V5 先定硬上限；超限明確不產連結。檔案分享若未來需要，再作獨立版本。這沒有新增後端或依賴。

## 4.5 儲存 canonical encoded payload，而非另一套展開 schema

- **嚴重度：Medium**
- **問題：** URL、記憶體與 localStorage 若各保存不同表示，會有三套去重、版本與完整性規則。
- **為什麼現在不修之後會更貴：** D41、切換模式及 codec 升版時容易漂移。
- **建議修法：** 若仍需持久化，選定單一 canonical formulary representation；URL 與 storage 共用相同版本化 payload，載入後才導出 matched subset。不得在讀取失敗時自行重寫修復。

## 4.6 不要為 D38 建第二套「估算可用性」模型

- **嚴重度：High**
- **問題：** `.size` 門檻與實際 quiz assembler 是兩套真相來源。
- **為什麼現在不修之後會更貴：** 題卷演算法調整後，availability UI 會再次漂移。
- **建議修法：** 可用性判定應重用實際組卷契約及 invariants，並把門檻只當快速拒絕條件。仍是純函式、零依賴，符合現有架構限制。
