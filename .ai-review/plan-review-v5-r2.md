# 第二輪規格覆審報告 — v5.2

## 總判定

**v5.2 尚不宜動工。**

主要原因是兩個 Blocker：

1. D38／D39 的短卷定義對 L1、L2 在數學上不可能成立。
2. D34 宣稱為不可變 wire contract，但 varint、CRC-32、base64url canonical 規則仍不足以產生跨版本唯一實作。

此外，D38 的非決定性可用性、未知前綴、D44 的跨 storage／memory／URL「原子提交」、U4 都應在凍結 v1 格式前解決。

其餘大方向已明顯成熟：16 種前綴修正、D37 誠實揭露資料集邊界、`records-fx` 移除、`content_hash` 配對、Actions staging、資料不進 SW 等均合理，不需重審或推翻。

# 1. 需求與邊界缺漏

## 1.1 未知前綴同時被「拒絕」、「分類」與「要求編碼」

- **嚴重度：High**
- **問題：** D35.2／A37 要求未知前綴必須拒絕；D37.1 又規定前綴不在 D34.4 者歸入「不在外觀資料集中」；D34.1 則要求連結保存全部 canonical id，但 D34.4 明說未知前綴無法編碼。三條無法同時成立。
- **為什麼現在不修之後會更貴：** tokenizer、分類、codec 與產連結 UI 會各自決定未知前綴是 invalid token、第三類 canonical id，或整份清單阻斷。這會直接改動資料模型與 v1 wire format。
- **建議修法：** 明定唯一裁決。最低代價是：未知前綴可列入第三類供揭露，但不是可編碼 canonical id，因此產連結前必須明確阻斷並要求移除；或現在就為 wire format 定義可攜帶未知前綴的 escape 表示。不可維持目前三種語意並存。

## 1.2 `excluded.json` 尚未形成完整資料契約

- **嚴重度：High**
- **問題：** 規格只描述 `{id, stage}` 與 `content_hash`，未正式定義頂層 schema、必要欄位、版本、id 唯一性、與 pool 的互斥規則、計數欄位，以及前端遇到單筆損毀時是否整檔失效。D47 的「schema 錯誤」目前只對 `pool.json` 寫得明確。
- **為什麼現在不修之後會更貴：** 管線、配對驗證及前端分類可能各自形成不同的實際 schema；一旦檔案發布，後補版本欄位或收緊合法性就會涉及相容處理。
- **建議修法：** 在規格中釘死 `excluded.json` 的版本化 schema、必要 metadata、items 契約、唯一／互斥不變量，以及「任一結構錯誤使整份 excluded 不可用、但不拖垮既有出題」的行為。

## 1.3 「明確指定 CSV 欄位」的互動契約仍不完整

- **嚴重度：Medium**
- **問題：** D35.1 已決定不得猜欄位，但沒有定義使用者如何指定：依欄名或欄序、是否有 header、delimiter 由誰決定、引號內 delimiter 是否算分欄、各列欄數不同時如何處理。
- **為什麼現在不修之後會更貴：** UI 與 tokenizer 會互相綁定未寫出的假設；取得 U1 後若檔案形式不同，解析與驗收都要改。
- **建議修法：** 只需補齊本版最小輸入契約，例如由使用者明確選 delimiter 與 1-based 欄序、header 是否略過、列結構不一致時整份拒絕。這是既有 CSV 路徑的必要定義，不是新增格式需求。

## 1.4 第三類的舊名稱仍散落在資料流與 C50

- **嚴重度：Low**
- **問題：** D37.1 已禁止「查無此證」式暗示，但 §5.2 仍寫「皆無 → 查無此證」，C50 也要求歸入「查無此證」。
- **為什麼現在不修之後會更貴：** 實作者可能把舊文字當正式 UI label，重新引入 v5.2 正要消除的誤導。
- **建議修法：** 統一改成中性的內部分類名稱與 D37.1 顯示名稱；若「查無此證」僅是內部代碼，須明說不得直接顯示。

# 2. 架構風險

## 2.1 D38／D39 的 L1、L2 短卷定義不可能成立

- **嚴重度：Blocker**
- **問題：** D39 規定短卷卷長等於 K，且正解集合恰等於全部 K 個鍵。但 H2 禁止其他題正解充當誘答，因此 L1 至少需要 `題數 + 3` 個答案鍵，L2 至少需要 `題數 + 5` 個。令題數等於 K 時，L1／L2 永遠沒有卷外誘答可用。只有無選項的 L3 能成立。A42 的 K=10／19 邊界及 A43 的 K=14 也建立在同一矛盾上。
- **為什麼現在不修之後會更貴：** 實作者只能改 H2、跨子集取誘答、偷偷減少題數，或讓 L1／L2 短卷全部禁用；前三者違反核心規格，最後一種又違反驗收。
- **建議修法：** 改成級別特定卷長，例如 L1 不得超過 `K−3`、L2 不得超過 `K−5`、L3 可等於 K；並刪除「短卷正解集合恰等於全部 K」對 L1／L2 的要求。若仍要求至少 10 題，級別最低 K 也須相應分開。

## 2.2 D34 尚不足以稱為不可變 wire contract

- **嚴重度：Blocker**
- **問題：**
  - 未指定 varint 是哪一種 unsigned 編碼、byte order、最大 byte 數、overflow 規則及號碼上限。
  - 未指定 CRC-32 variant：polynomial、初值、是否 reflected、final XOR；只寫「CRC-32」不足以跨實作一致。
  - 未明定 decoder 以何條件停止讀 groups，以及達到 `count` 後、checksum 前不得有剩餘 bytes。
  - 未定義 base64url 尾端未使用 bits 必須為零；否則同一 body 可能有多個字串表示。
  - `count=0` 是否為合法 payload 未定。
- **為什麼現在不修之後會更貴：** 任一實作一旦發布，都會成為事實上的 v1；之後修正只能升版並保留舊 decoder。
- **建議修法：** 在 D34.2／D34.3 補齊上述精確算法與界線，再由獨立 golden vectors 固化。

補充判斷：

- `count` 使用 uint16 與 D42 並**沒有實際容量衝突**；1800 字元 URL 能容納的 id 數遠低於 65535。
- 固定寬度 header 與 varint groups 混用本身沒有問題。
- CRC 涵蓋 `header ‖ groups` 已經明確；缺的是 CRC variant。
- groups 可由 `count` 自我定界，但必須把「恰好在 checksum 前解完，無多餘 bytes」寫成規則。

## 2.3 D38 的隨機 probe 會造成可用性抖動

- **嚴重度：High**
- **問題：** `drawLeveledQuiz` 是有限次重試的隨機貪婪組卷。同一子集可能 seed A 成功、seed B 失敗。D38 目前把一次隨機結果當級別可用性，且開始作答時若重新抽卷，可能出現「檢查時可用，按下後失敗」；重整頁面也可能讓按鈕忽隱忽現。
- **為什麼現在不修之後會更貴：** availability、UI 狀態與正式出題會形成三套時序；後補穩定性通常要改狀態模型與測試 RNG 契約。
- **建議修法：** 規格化一組固定、可重現且有界的 probe seeds；成功時保存該次已驗證的題卷，作為實際開始的第一卷，不得立即重抽。相同 payload、pool 與 level 的判定應穩定。

## 2.4 D44 要求的三介面「原子提交」無法真正交易化

- **嚴重度：High**
- **問題：** memory、localStorage 與 `history.replaceState` 沒有共同 transaction。storage 寫入成功後 URL 消費失敗，或 URL 先消費後 storage 失敗，都無法保證「任一步失敗時三者全部位元組不變」；回滾本身也可能失敗。
- **為什麼現在不修之後會更貴：** 實作者會寫出看似符合「單一 commit point」但實際存在中間態的流程，驗收則要求平台無法提供的保證。
- **建議修法：** 把 URL 消費降為成功提交後的冪等 cleanup，不納入交易。規格只要求：驗證完成前不發布；持久化成功後以不會拋錯的單一記憶體狀態切換發布；URL cleanup 失敗時保留 `fx`，但不得回滾已成功載入的清單。

## 2.5 U4 必須在凍結 wire v1 前裁決

- **嚴重度：High**
- **問題：** 這不只是 UI 限制，而是「payload 裝哪些 id」的資料模型問題。若實作後才從「全部 id」改成「來源已知 id」，v1 wire、storage identity、恢復語意與 recipient UI 都會改。
- **為什麼現在不修之後會更貴：** D34 已宣稱 v1 不可變；U1 到手後若證明常見全院清單超限，只能立即推出 v2 或推翻 D34.1。
- **建議修法：** 採最小代價方案：連結只攜帶「matched＋excluded」的來源已知 id；產生端仍完整揭露第三類及提供下載。
  **[新增需求]** 為避免 recipient 產生虛假完成感，payload 另攜帶「建立時未納入的第三類筆數」，載入端明示另有多少院內品項不在外觀資料集中。代價是第三類未來進資料集時不會自動恢復，但這比讓典型全院清單完全無法分享更符合本版核心用途。

## 2.6 `?v=` 的用途仍自相矛盾

- **嚴重度：Low**
- **問題：** D44.2 稱其「供顯示與診斷」，同時規定其值不得進 DOM。若不能顯示，實際只剩內部診斷；而目前又沒有診斷輸出契約。
- **為什麼現在不修之後會更貴：** 會增加 URL 狀態、消費規則及 C49 測試，但沒有明確使用者收益。
- **建議修法：** 最簡單是移除 `v`；顯示目前題庫版本時一律使用已驗證的 `pool.meta.source_version`。若保留，將用途改寫為「僅內部診斷，不顯示」。

# 3. 驗證策略缺口

## A36 — 16 種前綴與 27 組撞號

- **嚴重度：Medium**
- **問題／可通過的壞實作：** parser 只承認 16 個字串，但把 suffix、前導零或 canonical output 算錯；codec 的 prefix index 11–15 也可全部錯，因為 A36 只驗「解析」，不驗 wire index。
- **為什麼現在不修之後會更貴：** 前綴解析與編碼表可能各自全綠，直到跨版本連結才靜默指向錯藥。
- **建議修法：** 每個前綴都釘住精確 canonical id，並至少有一組獨立 wire golden vector 覆蓋新增的 index 11–15。測試資料不得由受測 normalizer 自己導出。

## A38 — golden vectors

- **嚴重度：High**
- **問題／可通過的壞實作：** 只 hardcode 接受少數 golden payload；或 golden 字串直接由受測 encoder 產生後抄回測試。單一小案例也可能完全沒碰到多組、multi-byte varint、CRC byte order 或新增前綴。
- **為什麼現在不修之後會更貴：** 「獨立 golden」若沒有獨立 oracle，仍只是 round-trip 的變形。
- **建議修法：** 規格要求 golden 的 body bytes 與最終 payload 均由獨立人工推導／第二來源確認，且矩陣涵蓋多 prefix group、multi-byte varint、0、最大合法號碼、新增前綴及 CRC byte order。

## A40 — 逐 byte 竄改

- **嚴重度：High**
- **問題／可通過的壞實作：** 所有語法損毀 fixture 都保留舊 CRC，decoder 只實作 CRC 檢查、不實作 canonical grammar，也會全部拋錯。另因規格允許「分段抽樣」，只翻 header／groups／checksum 各一 byte 也可宣稱完成。
- **為什麼現在不修之後會更貴：** 測試會證明 checksum 存在，卻錯誤宣稱 count、group order、最短 varint 等規則都被守住。
- **建議修法：** 分成兩類：bit-flip 測試保留舊 CRC，用來驗完整性；每個 grammar-invalid fixture 則重算正確 CRC，確保是 canonical validator 拒絕。並釘死實際 mutation 數與每區段非空，不能以模糊的「分段抽樣」代替逐 byte。

## A42 — 敵意子集

- **嚴重度：Blocker**
- **問題／可通過的壞實作：** availability 只用測試指定的單一 seed；敵意子集恰好在該 seed 失敗便通過，但其他 seed 又成功或一般子集反向失敗。更根本地，K=10／19／20 對三個級別共用同一預期，掩蓋了 L1／L2 額外誘答需求。
- **為什麼現在不修之後會更貴：** 測試會固化目前錯誤的短卷模型。
- **建議修法：** 先依 2.1 改成 level-specific 邊界，再用規格化的固定 seed 集合驗穩定 availability；成功案例必須使用 probe 產生的同一題卷，而不是另一次抽樣。

## B13 — 前綴表完整性

- **嚴重度：High**
- **問題／可通過的壞實作：** 若注入的未知前綴那筆剛好存活，僅掃 `pool.json` 的錯誤實作仍會通過，完全沒有堵住 v5.1 的真正失敗模式。只檢查錯誤訊息含字串，也允許永遠硬寫「1 筆」。
- **為什麼現在不修之後會更貴：** 這條會被當成「已防止再次漏表」，實際仍可能只掃存活集合。
- **建議修法：** 未知前綴 fixture 必須刻意在 Q1–Q5 被淘汰，且注入多筆並斷言精確筆數；如此只掃 pool 的版本必定失敗。前綴抽取也須明定發生在 allowlist 驗證之前，避免未知前綴先被 normalizer 丟掉。

## C43 — N／K 語意與靜態可及性

- **嚴重度：Medium**
- **問題／可通過的壞實作：** UI 對單一 fixture hardcode 正確 N/K；切級別、降級或換清單後仍顯示舊 K。靜態 scanner 只查節點自身的 `hidden`，卻漏掉 ancestor、class selector 或其他不可及屬性，也能通過。
- **為什麼現在不修之後會更貴：** 虛假完成感通常發生在狀態轉換後，不是在初始 fixture。
- **建議修法：** 增加同一 session 內 N 不變但 K 隨 level 改變、月更降級後 N/K 改變的精確斷言。靜態 scanner 須有反向 sentinel，分別證明自身能抓到直接 hidden、ancestor hidden 與規格列舉的不可及屬性；幾何與 CSS cascade 仍交給 C51。

## C50 — 惡意字串與 sink call log

- **嚴重度：Medium**
- **問題／可通過的壞實作：** token 在 normalization 前就被丟棄，因而所有 dangerous sink call log 都是零；或實作用樁未監控的 property assignment／DOM API 寫入 attribute，仍可通過。
- **為什麼現在不修之後會更貴：** 「零 sink 呼叫」可能只是惡意資料從未到達受測路徑，或監控面不完整。
- **建議修法：** 先斷言該 token 確實經真實 tokenizer 到達第三類、顯示資料與下載資料，再驗 sink。規格須列出零依賴樁實際監控的完整 sink inventory，並用 sentinel 證明每種監控都能被觸發；不得引入 jsdom。

## C51 — 人工留檔矩陣

- **嚴重度：Medium**
- **問題／可通過的壞實作：** 四張經裁切或挑選的截圖看似正常，但沒有證明互動 hit box ≥44px；也可能截圖資料與標註的 N/K 不同。
- **為什麼現在不修之後會更貴：** 觸控目標通常到手機實測才發現，屆時需回改 layout。
- **建議修法：** 留檔需包含完整畫面、瀏覽器與 zoom、viewport、fixture identity、實際 N/K，以及觸控目標尺寸的人工量測紀錄；四種狀態逐張獨立 verdict，不得只以視覺估計「看起來夠大」。不需新增 jsdom 或瀏覽器自動化。

# 4. 更簡單的替代方案

## 4.1 U4：不攜帶第三類 id，只攜帶第三類計數

- **嚴重度：High**
- **問題：** 編碼全部 id 的恢復收益，對第三類而言高度不確定；但它們會讓常見全院清單直接超過 1800 字元。
- **為什麼現在不修之後會更貴：** v1 發布後再改集合語意，需要升 wire version 與 storage migration。
- **建議修法：** 採 2.5 的「來源已知 id＋第三類 count」方案。這是目前最小改動、仍能防虛假完成感、又不新增後端或檔案 fallback 的解法。

## 4.2 D38：availability 直接產生「已備妥的第一卷」

- **嚴重度：High**
- **問題：** 目前先為 availability 抽一次，再為正式開始抽一次，重複成本且允許兩次結果矛盾。
- **為什麼現在不修之後會更貴：** 會增加競態、RNG 抖動與 UI 狀態。
- **建議修法：** 把成功 probe 的題卷定義為 ready state 的一部分。這不是第二套可用性模型，而是直接重用真實產物，符合 D48。

## 4.3 刪除沒有決策用途的 `?v=`

- **嚴重度：Low**
- **問題：** `v` 不阻斷、不得進 DOM，也不參與 codec，收益不足以抵銷 URL 與消費規則。
- **為什麼現在不修之後會更貴：** 一旦外部連結帶上它，就要永久維護解析與相容行為。
- **建議修法：** v5 不攜帶 `v`；診斷與顯示使用當前已驗證 pool metadata。

## 4.4 其餘主要複雜度並未失衡

- **嚴重度：Low**
- **問題：** binary codec、CRC、16 種版本化前綴、獨立 `excluded.json` 與 Actions staging 看似繁複，但各自對應 URL 上限、靜默錯藥、既有流量隔離與全有全無發布。
- **為什麼現在不修之後會更貴：** 若為簡化而合併檔案、取消 checksum 或改回 pool index，會重新引入已知高風險。
