## 兩項 High

### R3-1 canonical id 的文字重建規則未定 — **接受**

**已實測確認，且這是會讓整個功能靜默失效的那種缺口。**

```
來源 6295 列的號碼段字元長度分布：{"6": 6295}   ← 100% 固定 6 字元，零例外
  一般型：6 位數（前導零補足）      R 型：R ＋ 5 位數
```

D34 把號碼整數化編碼，卻**沒寫解碼時怎麼還原成字串**。若不補零，
decoder 產生 `衛署藥製字第123號` 而非 `衛署藥製字第000123號`——
而 join key 是**字串完全相等**，結果是**全部比對為未命中**。
encoder 看起來完全正常，測試若只跑 round-trip 也全綠。

Codex 另抓到我在 D34.4 表中的不一致：**index 0–15 寫成不含「第」的 `衛署藥製字`，
index 16–17 卻寫成含「第R」的 `衛署藥輸字第R`**——同一張表兩種格式。
這是我在 v5.3 補字母變體時留下的。

修法：新增 **normative 表**（併 R3-10），逐 index 列出精確前綴字串、
數字寬度、最小／最大值、以及一個 reconstructed canonical id 範例；
並明定 `prefixIndex` 超出該版本表範圍必須拒絕。

### R3-2 D38.3 的 seed 協定未規格化 — **接受**

屬實。我寫了「規格化的固定 seed 序列」——**「規格化的」三個字本身就是待辦事項，不是規格。**
缺 seed 導出方式、PRNG、單一 stream 或多 top-level seeds、subset 排序。

**Codex 的查核有價值**：它確認引擎內部沒有漏網隨機源，所以問題純粹在協定沒寫，
不必動組卷模型。兩個實作者可以都完全不碰 `Math.random`，卻對同一 payload
判出不同 availability。

修法採 R3-9 的最簡版：payload ＋ level 導出**單一 32-bit seed** →
指定 PRNG（沿用 `engine.js` 既有的 `makeRng`）→ 單一 stream 交給既有
`MAX_QUIZ_ATTEMPTS` 消耗。**不在外層再疊一層多 seed 重試**。

## 逐項判定

| # | 項目 | 嚴重度 | 判定 | 理由 |
|---|------|---|------|------|
| **R3-1** | canonical id 重建規則未定 | High | **接受** | 見上。實測 6295/6295 固定 6 字元 |
| **R3-2** | seed 協定未規格化 | High | **接受** | 見上。採 R3-9 的單一 seed 最簡版 |
| **R3-3** | `unlistedCount` 語意與 uint16 邊界未封閉 | Medium | **接受** | 屬實。第三類沒有 canonical id，所以「算什麼」必須明講：是原始 token 數、正規化後相異值數、還是去重後品項數？三者不同就會產生不同 header 與不同 CRC。修法：定為**正規化後去重的相異 token 數**；兩個 uint16 欄位**超界一律拒絕，不得截斷或 modulo** |
| **R3-4** | 「冪等」可能被誤讀成 storage 位元組冪等 | Low | **接受** | 屬實且細膩。D45 的 `savedAt` 讓同一 `fx` 重播必然產生不同位元組——我寫「結果相同（冪等）」時沒想到自己的 schema 裡有時間戳。修法：明寫「**URL cleanup 操作冪等；重播同一 payload 的 active formulary 語意相同**」，不宣稱 storage bytes 不變 |
| **R3-5** | A39 要求「邊界號碼 0」但 D34.3 定 ≥1 | Medium | **接受** | **我自己的矛盾，第七個。** 修法：A39 的合法邊界改為 1；號碼 0 移到 A40 的 grammar-invalid（重算正確 CRC 後斷言拒絕） |
| **R3-6** | A43 的 L2 用 K=14，但 D38.1 定 L2 最低 K=15 | Medium | **接受** | **我自己的矛盾，第八個——而且 A43 與 D38.1 是同一次編輯寫的。** A42 說 K=14 禁用、A43 說 K=14 有可驗題卷，實作無法同時滿足。修法：A43 的 L2 fixture 改 K=15（預期 10 題）；K=14 只留在 A42 驗禁用 |
| **R3-7** | 沒有驗收證明「probe 產物就是第一卷」 | Medium | **接受** | 屬實。D38.3 寫了這條要求，但 A42 只驗 availability 可重現、C41 只驗封閉性——**實作仍可在按開始時重抽一次而全綠**。這正是第二輪「檢查時成功、開始時失敗」的復發路徑。修法：新增跨層驗收，記錄 probe 題卷的穩定 identity，開始後逐題斷言同一產物，且**開始動作沒有第二次組卷或額外 RNG 消耗** |
| **R3-8** | golden 未覆蓋 `unlistedCount` 與 prefixIndex 越界 | Medium | **接受** | 屬實。codec 可以**完全忽略 `unlistedCount`**（那是 v5.3 才加的欄位），現有 golden 仍會通過。修法：golden 至少含 `count=0, unlistedCount>0` 與一般非零兩種；grammar-invalid 加兩個 uint16 邊界與 prefixIndex 越界 |
| **R3-9** | 「固定 seed 序列」易被實作成兩層重試 | Low | **接受** | 屬實。我的措辭確實會讓人在 `drawLeveledQuiz` 外再疊一層。併入 R3-2 的修法 |

## 這一輪的通則

### 一、「規格化的 X」不是規格

R3-2 的核心：我寫「**規格化的**固定 seed 序列」，讀起來像已經定義，
實際上「規格化的」三個字是**待辦事項的形容詞化**。
同型的還有 v5.0 的「須包含各種案例」、「驗證 A 與 B 對應」。

**判準：一個名詞前面加上形容詞不會讓它變成契約。
問「兩個獨立實作者看到這句話，會做出位元組相同的東西嗎？」**

### 二、「編碼」與「解碼還原」是兩件事，我只寫了一半

R3-1 是本輪最危險的一項：D34 花了大量篇幅定義**怎麼把 id 變成 bytes**，
卻沒寫**怎麼把 bytes 變回那個字串**。而後者才是 join key 成立的條件。
整數化是有損的——遺失的正是前導零。

**通則：任何「A → B」的編碼規格，必須同時寫「B → A」的還原規格，
並明確指出哪些資訊在轉換中遺失、由什麼規則補回。**
