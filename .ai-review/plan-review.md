結論：整體方向可行，D1、D2、D6、D7 都符合既定限制。動工前最需要先定案的是：

- 「英文品牌名」與資料實際只能產生「英文品名核心字串」的語意落差。
- 題目可解性不能只用「標註一非空」代表。
- 圖片、來源紀錄、答案鍵之間缺少可驗證的一對一身分關係。
- C4 的「離線重新整理仍可作答」與圖片 lazy load 互相矛盾。
- 資料更新目前容許大量題目因暫時性下載失敗而靜默消失。

以下僅審規格，未進行任何檔案操作，也不涉及程式碼實作。

## 1. 需求與邊界缺漏

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | 目標要求輸入「英文品牌名」，但 TFDA 英文品名欄同時包含品牌、學名式品名、廠商與規格；例如 `SODIUM BICARBONATE` 並不是品牌名。D3 的字串剝離無法判斷哪段在語意上是品牌。 | UI、提示、答案、檢討與免責聲明都會建立在錯誤的教育宣稱上。完成後才發現時，可能必須重建答案資料，甚至 join 另一資料集或人工整理。 | 相容既有非目標的作法是把目標與 UI 用語改成「英文品名核心字串」，明示可能包含品牌名或通用式品名。若堅持「品牌名」，就需要額外資料映射或人工策展；這與「不 join 其他資料集」的既定取捨衝突，應另行決策。 |
| **High** | D4 把「標註一非空」等同於「題目可解」，但非空刻字不保證唯一性，也不排除標註錯誤、共用刻字或兩個不同答案具有相同外觀。 | 題庫完成後才發現不可解題，會牽涉題庫資格規則、抽題邏輯、歷史圖片與既有答案一起重整。更重要的是，使用者可能因合理答案被判錯而學到錯誤資訊。 | 把「題目可解」定義成明確的題庫資格條件，而不是只寫「有刻字」。至少規定如何處理相同或高度相似的 `mark1/mark2 + shape + color` 卻有不同答案鍵的群組。若要求人工確認疑似衝突群組，應標為 **[新增需求]**；不做的可觀察後果是存在外觀無法區分、卻只接受單一答案的題目。 |
| **High** | `pool.json` 的資料模型沒有來源版本日期或題庫產生日期，但 C5 要顯示「資料版本日期」。 | UI 完成後才補會改動 pool 的頂層格式、資料載入假設、測試 fixture 與 Service Worker 相容性。 | 動工前定義版本日期的語意與存放位置：是 TFDA 資料版本、下載日期、成功發布日期，或內容雜湊所代表的版本。不可只由瀏覽器推測檔案時間。 |
| **Medium** | 作答狀態機未定義：答錯後能否重試、何時鎖定、是否自動進下一題、答錯後能否再取提示、重複按送出是否重複計分。 | app 完成後才決定會重寫事件流程、計分狀態與逐題檢討資料；也可能出現反覆嘗試直到答對仍得滿分的漏洞。 | 明定每題狀態及合法轉移，至少涵蓋：未作答、已提示、已提交、已鎖定、資源載入失敗。並明定首次答案或最終答案哪一個決定分數。 |
| **Medium** | 未定義空輸入、只有空白、過長輸入、全形英數、Unicode 變體及非 Latin 字元的判定邊界。 | 正規化與 UI 驗證各自形成不同規則後，再統一會修改既有測試與作答紀錄模型。 | 在 D3/D6 中補一份執行期輸入契約，明定哪些輸入先拒絕、哪些進入 normalize、長度計算採何種字元定義。這是既有作答需求的邊界釐清，不是新增功能。 |
| **Medium** | 提示的「首字母與字數」對多字答案不明確；範例也未說空白、連字號是否計入。 | 提示 UI 和測試完成後才修，會同時影響顯示、字數計算及不同答案的公平性。 | 明定提示依據是正規化答案、去空白答案，或逐字顯示 word boundary；字數規則必須與範例一致。 |
| **Medium** | 「隨機抽 20 題」沒有定義抽樣單位。依紀錄均勻抽樣會讓 `IBUPROFEN ×20` 等重複答案鍵獲得較高出題權重，即使同卷去重仍然如此。 | 上線後若要改成答案鍵均勻抽樣，題目分布、難度與測試統計都會改變。 | 在規格中選定「紀錄均勻」或「答案鍵均勻後再選一個外觀」，並把這視為教育分布決策，而非留給實作自行決定。 |
| **Medium** | pool 或圖片載入失敗時的行為未定義。尤其圖片 decode 失敗若仍允許作答，會形成無圖題；若算錯則污染成績。 | 錯誤狀態若晚加，會穿透抽題、計分、進度與檢討流程。 | 明定資源失敗不得轉化成答錯；規定重試、換題或中止本回合中的一種一致行為，且不計入 20 題分母。 |

## 2. 架構風險

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | 圖片只在「新增或 URL 變更」時下載，無法偵測同一 URL 下內容被 TFDA 替換。這可能造成新 metadata 配舊圖片，或永遠保留錯誤圖片。 | 一旦錯誤資產進入 repo，後續增量流程不會自行修正；數年後也很難追溯從哪次更新開始錯配。 | 保留「只能由 Actions 抓取」及「圖檔鏡像 repo」不變，但規格需定義圖片內容變更的偵測或定期重新核對政策，以及 metadata、來源 URL、鏡像內容必須屬於同一資料快照的發布不變量。 |
| **High** | `許可證字號 → slug` 的規則沒有定義，也沒有要求 slug 唯一。B4 只檢查檔案存在；若兩個 ID slug 碰撞，仍會通過但可能顯示錯藥圖片。 | 命名方式一旦被大量檔案、Git 歷史和 pool 引用，就很難更換；這是整份規格最難回頭的決策之一。 | 在資料模型中規定資產鍵必須是可證明一對一或經全題庫驗證無碰撞的識別值，並驗證每筆來源紀錄只對應自己的圖片。 |
| **High** | 首次本機 seed 與每月 CI 增量是兩條資料產生路徑，但未要求兩者使用完全相同的篩選、正規化、圖片轉換與驗證規則。 | 首批 4,086 張若有錯配，因 URL 未變而可能永遠不再下載；之後 CI 即使正確也無法修復基線。 | 把 seed 定義為同一資料管線的首次完整模式，而不是獨立腳本或獨立規則；首批資料也必須通過所有 B 組驗證後才能成為基線。 |
| **High** | C4 要求「斷網重新整理後仍可作答」，但 Service Worker 只列出快取 pool 與 app；隨機抽出的圖片仍是 lazy load，斷網時通常不存在。若要保證任意 20 題，等同要求預存全部圖片。 | 實作後才發現會被迫在「快取約 60MB 全題庫」「改變離線語意」「放棄 lazy load」間重新選架構。 | 建議把 C4 改為「已載入的本回合在斷網後可繼續」，或直接移除離線重新整理要求。這與純靜態限制相容。若堅持重新整理後可開始任意新回合，必須明確承認全題庫圖片快取及裝置儲存配額是需求。 |
| **High** | Service Worker 可能讓新版 `pool.json` 與舊版 engine/app、或新版 pool 與舊圖片同時存在，形成版本錯配。此風險直接影響答案與圖片對應。 | pool 格式或正規化規則一旦演進，沒有版本相容契約會造成難以重現的客戶端錯誤；清除快取也無法修復已發生的錯誤學習。 | 若保留 Service Worker，規格需要求同一發布版本的 app、pool 與資產一致切換，並定義舊快取淘汰及不相容版本的處理。更簡單的相容方案是移除 C4 與 Service Worker。 |
| **High** | 暫時性圖片下載失敗會直接把該筆從 pool 剔除，而 B3 允許從預期 4,086 筆降到 3,500 筆仍發布。這使 586 筆以上可因網路問題靜默消失。 | 錯誤快照可能被自動 commit 並成為新基線，下次比較反而把大量遺失視為正常。恢復時也會造成巨大 diff。 | 區分「來源本身已移除／失去圖片」與「本次下載失敗」。後者應使整次發布失敗或維持上一版，不得用刪題吸收。除絕對下限外，還要有相對於上一成功版本的異常增減門檻。 |
| **Medium** | 圖片更新與刪題後，舊資產如何處理未定義。若永不刪除，repo 工作樹及 Git 歷史會持續增加；二進位檔每次替換也會累積歷史容量。 | 五年後才處理可能需要大規模重寫 Git 歷史或更換託管方式，代價遠高於現在定義生命週期。 | 不改變 D2，但現在就定義孤兒圖片政策、年度容量預算、警戒門檻，以及超過預算時的人工決策點。 |
| **Medium** | 排程與手動觸發可能同時執行，兩個 job 都從不同基線產生並嘗試發布。 | 初期不常發生，但一旦發生會造成非快轉失敗、重複摘要，或人工誤把其中一次失敗當資料問題。 | 規格層要求同一資料分支上的更新序列化；後啟動的任務應取消、等待或基於最新成功版本重新驗證。 |

## 3. 驗證策略缺口

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | A1/A2 只驗證正規化「有輸出」和少量字串案例，不能證明輸出真的是正確品名，更不能證明沒有把品牌關鍵字剝掉。A4 也只驗證碰撞，不驗證語意。 | 正規化規則完成後才建立語意基準，可能揭露整批答案鍵需重算，連帶使圖片、檢討內容與既有測試失效。 | 增加一組固定、人工確認且涵蓋不同命名型態的 gold set，驗證原始英文品名到答案鍵的期望映射。這是驗證既有答案正確性，不是新增產品功能。 |
| **High** | 沒有任何驗收條件能證明某張 WebP 真的是該許可證字號的圖片。B4 只證明路徑存在。 | slug 碰撞、錯誤 rename、seed 錯配或轉檔輸入錯誤都能在全部 B 測試通過後進入正式題庫。 | B 組需加入來源紀錄、來源圖片與鏡像資產的一對一關係驗證；至少能偵測兩個不同 ID 指向同一個非預期資產，或資產由錯誤來源產生。 |
| **High** | B3 的固定下限 `≥3500` 過於寬鬆，不能偵測從 4,086 大幅下降至 3,500 的靜默退化。 | 首次異常發布後，下降後的數字會成為事實基線，後續難以確認哪些題目是合法移除。 | 同時驗證：來源總筆數、各篩選階段筆數、最終筆數、與上一成功版本的增減幅度。超過合理變動時必須 fail，而非只輸出摘要。 |
| **High** | C 組沒有測 pool 載入失敗、JSON schema 不相容、少於 20 個不同答案鍵、圖片 404／decode 失敗等關鍵錯誤路徑。 | 這些失敗會穿過抽題與計分，最後可能被當成使用者答錯；後補會修改整個狀態流程。 | 增加可證偽條件：上述狀況不得開始或完成一份含無效題目的考卷，不得計入錯誤與分數，且應呈現明確失敗狀態。 |
| **Medium** | A4 寫「碰撞非 0 就逐一列出並調整門檻」，因此不是固定的 pass/fail 規格；「如何調整」也未定義。 | 實作時可能為了讓測試通過任意提高門檻，或針對個案加入例外，導致判定政策漂移。 | 動工前定義碰撞處理順序，例如排除特定答案、對特定答案禁用容錯，或調整全域長度門檻；任何調整後仍必須保持零跨答案誤接受。 |
| **Medium** | A4 的「長度 ≥6」未說是含空白或不含空白，也未說不同長度答案比較時看哪一方。 | 測試與執行期可能各自採不同長度定義，使已驗證的零碰撞不等於實際判定零碰撞。 | 與提示規則一起統一長度定義，明定以儲存的答案鍵、去空白答案鍵或使用者輸入哪一者判斷。 |
| **Medium** | A5 用 1,000 次隨機抽題只能提高信心，不能證明不變量，且可能形成不可重現的偶發失敗；也沒測 0、19、20 個不同答案鍵的邊界。 | 抽題演算法換動後仍可能通過 1,000 次，直到正式環境遇到稀有路徑才卡死或少題。 | 驗收應以「所有輸出必須符合不變量」及明確邊界案例為主；隨機重跑只能作補充，不應是唯一證據。 |
| **Medium** | B2 使用 `glob *.json` 只證明不硬編碼檔名，未定義 ZIP 中有零個、多個 JSON，或其中一個是 metadata 時應如何處理。 | 上游一旦增加第二個 JSON，管線可能選錯、合併重複或依檔案列舉順序產生不穩定結果。 | 定義資料檔的 schema 辨識規則，並明定零個或多個符合資料 schema 時是 fail 還是合併；不可依任意 glob 順序選第一個。 |
| **Medium** | B1 的「data 維持不變」若只在失敗 job 的暫存工作目錄驗證，不能證明既有正式版本未被部分發布；也未涵蓋 HTTP 200 但內容不是合法 ZIP/JSON。 | 自動 commit 流程完成後才補發布原子性，會重整管線步驟與測試環境。 | 將 B1 擴充為「任何抓取、解壓、schema、數量或圖片驗證失敗，都不得產生新的可發布版本或 commit」。 |
| **Medium** | B5 的冪等要求可能與「資料版本日期」衝突：若每次抓取都更新下載日期，即使來源未變也會產生 diff。 | 之後才發現會被迫修改版本語意、摘要格式或放棄冪等測試。 | 明定 pool 內只保存內容版本或來源版本；本次執行時間若要留存，不應影響已聲明的內容冪等性。 |
| **Medium** | B4 沒驗證圖片可解碼、實際為 WebP、尺寸合理、非零位元組或非錯誤頁轉檔結果。 | 損壞檔案在 repo 中「存在」但瀏覽器無法顯示，問題直到前端或使用者端才被發現。 | 將「存在」提升成「可解碼且符合輸出資產契約」，並把失敗視為整次資料發布失敗。 |
| **Medium** | C1 的 `<3MB` 沒定義是原始大小、HTTP 壓縮後傳輸量、冷快取或包含字型及其他資產。 | 不同測試環境會得到不同答案，使條件表面可證偽、實際無法一致判定。 | 定義測量情境與範圍，例如正式 Pages、冷快取、特定網路請求集合，以及使用傳輸量或未壓縮大小。 |
| **Low** | C3 要求成績卡「無破圖」，但 D7 已明定成績卡只有文字與色塊，不包含藥品圖片。 | 測試者無法判斷「破圖」實際指什麼，可能建立無效驗收。 | 改成可觀察條件，例如 PNG 可解碼、尺寸正確、文字未截斷、中文 glyph 正常。 |

## 4. 更簡單的替代方案

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | Service Worker 只為 C4 存在，但離線並未列在目標中，且它引入快取版本錯配、圖片離線範圍與更新一致性問題。 | 一旦上線並註冊，後續移除仍要處理使用者瀏覽器中的既有 worker 與舊快取。 | 最簡方案是 v1 移除 C4 與 Service Worker，依瀏覽器一般 HTTP cache 運作。若保留離線價值，將條件縮成「已載入的本回合可繼續」，不承諾離線重新整理後開始新考卷。 |
| **High** | 每月自動更新完整公開題庫，對「外觀辨識自我測驗」不是必要條件，卻把上游資料變動直接變成教育內容變動。 | 自動發布建立後，資料漂移、題目刪除與圖片替換都需要長期監控；五年維護成本可能高於前端本身。 | 更簡單且符合靜態架構的方案是採「已驗證快照」：資料抓取與驗證可自動進行，但正式題庫僅在摘要及異常檢查完成後人工觸發更新。這不新增使用者功能，也不需要後端。 |
| **High** | 4,086 題全量收錄增加圖片種子、命名、更新與語意正規化風險，但目標只要求每回合 20 題，沒有要求涵蓋全部合格紀錄。 | 全量資料一旦成為對外承諾，之後縮減會被視為內容退步；同時每一筆都成為可能誤導藥師的責任面。 | 可考慮先使用較小、經人工確認的高可信題庫，再逐批擴充。若要求人工審核後才能納入，這是 **[新增需求]**；不做的可觀察後果是低品質、不可解或答案語意錯誤的紀錄可直接進入教學題庫。 |
| **Low** | engine/UI 分離、repo 內 WebP 鏡像、純 Canvas 成績卡看起來不是 over-engineering；反而直接服務可測試性、流量與 CORS 限制。 | 若為追求「更簡單」而合併 engine 與 DOM、恢復外連圖片或引入 DOM 截圖依賴，會破壞已驗證的平台條件。 | 維持 D1、D2、D6、D7。不要導入 bundler、React、CORS proxy 或外部截圖套件；這些方案都與前提 (a) 明確衝突。 |

整體判定：**可行，但不建議依 v1 原文直接動工**。至少應先解除「品牌名語意」、題目可解性、圖片身分關係、失敗時不得縮水發布，以及 C4 離線範圍這五個規格歧義。
