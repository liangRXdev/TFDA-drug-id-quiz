## 三個真 Blocker

### 2.1 D38 把 `eligibleKeys.size` 當成「一定組得出卷」— **接受**

**這是 M5 的 M-11 同型錯誤，而且是我自己寫進 `verdict-m5.md` 的教訓。**
那條的原文是：「注入點在防線前面，等於沒測……每個鍵單獨看都 eligible
（前置檢查放行），但整卷的 `excludeAns` 使第 2 題起湊不出誘答」。

`eligibleKeys()` 是**逐鍵局部判定**（`recordEligible` 不看整卷脈絡），
而 `drawLeveledQuiz` 的 `excludeAns` 恆為**整卷正解集合**（H2），
因此 `.size >= 20` 與「能組出 20 題」之間沒有蘊含關係，
`QUIZ_ASSEMBLY_FAILED` 仍可能發生。D38 的整張門檻表因此**不是可用性證據**。

嚴重度正確：UI 宣稱可用、按下去才失敗，而「救場」的兩條路
（重複題／跨子集誘答）各自違反 H2 與 D36——**正好是本專案兩個核心約束**。

修法採 Codex 建議並與 4.6 合併：可用性判定**重用真實組卷路徑**
（實際跑一次 `drawLeveledQuiz` 並過 `validateQuizInvariants()`），
`.size` 門檻降級為**快速前置拒絕**，不是最終證據。

### 2.2 A40 要求的完整性偵測，D34 的格式做不到 — **接受**

屬實且是**「規格文字強於任何合理實作能達成的範圍」的第三次**
（前兩次：`plan-v4-engagement.md` 的 D10「增量判定含 src_sha256 不符」、
D27「JS 不得自帶動畫」）。

delta＋varint 沒有任何冗餘位元，中段 bit flip 極可能仍解出一組合法遞增序列，
只是指到另一批藥證字號。A40 寫「中段位元竄改必須拋錯」在這個格式下**不可能成立**——
若照寫，實作只能對四個 fixture hardcode 拒絕，**製造出本 repo 最危險的那種假綠燈**。

修法：**D34 補完 wire format**（格式版本、prefix table 版本、count、canonical varint、
尾端 checksum），A40 才站得住。這也一併解決 1.13 的 canonical grammar 與 2.3 的前綴表版本化。

### 1.4 上傳內容的 tokenization 未定義 — **接受**

屬實。D35 只定義了**單一 token 的正規化**，完全沒定義**怎麼把一坨文字切成 token**。
BOM、引號、全形逗號、空列、混在中間的說明文字、一列多欄——每一項都會讓
parser 與測試 fixture 綁死不同假設。

我原本把它掛在 U3「暫定兩者都做」，這是**把決策當成待辦事項**，
而 Codex 正確指出它是**契約**不是待辦。修法：本版定義正式輸入契約
（純文字每行一個 token 為唯一正式格式；CSV 需明確指定欄位，無法判定時**拒絕而非猜測**）。
